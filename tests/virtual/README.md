# The virtual gateway

This folder holds a copy of the gateway built from Linux network namespaces: a namespace TV, a namespace gateway that runs the real `tvgw-apply`, and a namespace internet. The suite checks every ruleset variant with `nft -c` and probes the loaded firewall from the TV's side, so a firewall change is exercised on a kernel before it reaches the gateway. It runs as root on a Linux machine or VM, and in CI's `virtual` workflow on every pull request and every push to `main`. It is for developers changing `deploy/nftables/tvgw-apply` or anything the firewall reads. The kinds of tests and where each runs are in [the tests overview](../README.md); why the suite exists and how it stays off the host's files is [design decision 27](../../docs/design-decisions.md#27-a-namespace-copy-of-the-gateway-in-ci).

## The topology

| Namespace | Interfaces and addresses | What runs there |
|---|---|---|
| `tv` | `eth0` 10.10.10.50/24, plus 10.99.0.5/32 as a foreign source and 10.10.10.200/32 as a second address in the TV subnet (the pin's case); default via 10.10.10.1 | The probes; a TCP service on 8000 for the unsolicited-inbound row; from `test_virtual_discover.py` on, TCP 8060 on 10.10.10.50, Roku's LAN-API port, for discovery's probe |
| `gw` | `eth0` 10.10.10.1/24 to the TV; `wlan0` 198.51.100.2/24 and `tun0` 192.0.2.2/24 to the internet; main default via `tun0`, as the VPN client's routes are on the gateway | `tvgw-apply`; a stand-in AdGuard (answers every query with 198.51.100.153), nginx (TCP 80 and 443) and one other Pi service (TCP 8000, UDP 5000) |
| `wan` | `up0` 198.51.100.1/24 (the router), `vpn0` 192.0.2.1/24, and on `lo` 203.0.113.10 (web), .20 (a DoH resolver), .30 (a manual block), .53 (a public resolver), 10.20.30.40 (a home-LAN host) and 156.147.69.32 (LG's firmware fallback) | A public resolver (answers 203.0.113.153), TCP and UDP services on every port a row names, a GRE echo |
| `chk` | dummy `eth0` and `wlan0` | Only `tvgw-apply --check` |

The gateway namespace keeps reverse-path filtering loose (`net.ipv4.conf.all.rp_filter=2`, as systemd leaves it on the gateway), so the `rp_filter=1` `tvgw-apply` sets on `eth0` stays loose in effect, as there, and a forged source reaches the firewall rule that must drop and count it. Its per-destination ICMP limit is off (`net.ipv4.icmp_ratelimit=0`; the kernel's default, on the gateway too, is one a second with a burst of six): a refusal by a rule that answers with ICMP (DoT and DoQ, QUIC, the manual blocks, `STRICT_PORTS`) is an ICMP error to the TV, and the seventh within a few seconds would be held back and read as a drop the firewall did not make. The gateway namespace uses the default interface names of the settings (`eth0` and `wlan0`), and its tunnel is `tun0`, the first name `VPN_IF=auto` looks for, so vpn mode finds it as it would on the gateway; a namespace has names of its own, so nothing on the host is renamed. With `TVGW_VIRTUAL_IFNAMES=alt` the same ports are `tvport0`, `uplink0` and `wg0` ([other interface names](#other-interface-names)). Every service reports the source address it saw, so a probe knows whether its connection left by `wlan0` (198.51.100.2), by `tun0` (192.0.2.2) or was not NATed at all. The stand-ins are one stdlib-only script, `agent.py`, run inside each namespace.

`tvgw-apply` sources `/etc/tvgw/tvgw.conf` and writes `/run/tvgw`, with no override for either. The suite runs it under `unshare --mount` inside the gateway namespace with a temporary directory bind-mounted over each of `/etc/tvgw`, `/var/lib/tvgw` and `/run/tvgw`, and a tmpfs over `/run/lock`. The host's own files are never written, so the suite cannot overwrite a real gateway's settings or the baseline `tvgw verify` reads, even when it is run on one. The conf holds `WAN_IF=wlan0`, `WAN_GW=198.51.100.1`, `TV_IP=10.10.10.50` and `TV_MAC=02:00:00:00:00:50` (a locally administered placeholder, so the forward pin is loaded) and the scenario's switches; `block4.txt` holds 203.0.113.30 and `doh4.txt` holds 203.0.113.20. When `/etc/tvgw`, `/var/lib/tvgw` or `/run/tvgw` does not exist, the suite creates it as an empty mount point and removes it afterwards.

## The reachability matrix

`matrix.txt` is the expected behaviour of the firewall, as data. A `[name] KEY=value ...` line opens a scenario; each row after it is one probe:

```text
[direct] UPLINK=direct BLOCK_QUIC=yes STRICT_PORTS=no DNSGATE=count
tv          tcp      203.0.113.20   443   reject           DoH resolvers
```

| Field | Values |
|---|---|
| source | `tv`, `tv-foreign` (the TV's link with source 10.99.0.5), `tv-alias` (source 10.10.10.200), `wan`, or (probe) `probe` (the probe's port, source 10.10.10.30) and `probe-alias` (source 10.10.10.31) |
| probe | `dns-udp`, `dns-tcp`, `tcp`, `udp`, `ping` (the port field is the payload size), `gre`, `udp6` |
| target, port | the address and port probed; `-` for none |
| verdict | `pass:tv`, `pass:wlan0`, `pass:tun0` (where the far end saw the connection come from), `pass` (ping, GRE), `answer:gateway` or `answer:wan` (which resolver answered), `reject` (refused at once: a reset or an ICMP unreachable), `drop` (silence for 1.5 s), `sent` (only the counter can judge) |
| counter | the comment of the rule whose counter must gain at least one packet, or `-` |

A row passes when the probe saw the verdict, the named counter moved, and no other drop or reject counter moved; `no IPv6 from the TV` is exempt from the last check, because neighbour discovery on the TV link ticks it on its own. A fifth scenario, `probe` (`TV_PROBE=on`), probes from the probe's port: source `probe` is a client on the pair `tvgw-apply`'s probe rules name, with the probe's address 10.10.10.30, and `probe-alias` a second address on that port, 10.10.10.31. Its rows name no counter, since the probe's rules have none, so each also says that no drop or reject counter of the TV's moved; the second address gets nothing. In `direct`, where the probe is off, one row shows the same port forwarding nothing. The four other scenarios are the shipped default (`direct`), QUIC open with `STRICT_PORTS=yes` and the gate off (`strict`), the VPN as the uplink (`vpn`), and the general profile (`generic`, `PROFILE=generic-tv`), where no LG port wall is built and TCP 4431 is counted by the odd-port rule like any other port. A scenario header may name `PROFILE` beside the four switches. The rows cover the guarantees the hardware suite trusts: DNS to any resolver lands on the gateway's resolver, DoT, DoQ, DoH-by-IP, QUIC and manual blocks are refused, TCP 4431 is reset by the adtech port wall before the odd-port rules see it (in `direct` and in `strict`, where the `STRICT_PORTS` counter must stay still), the home LAN and the gateway's other ports are dropped, a foreign source is dropped (forwarded, and at the gateway's input), a second address in the TV subnet is not forwarded, tunnels and large pings are dropped, the web is reached by the chosen uplink only, and nothing unsolicited gets in from the internet or the VPN side.

A firewall change that changes what the TV can reach changes a row, so it arrives as a reviewed diff of `matrix.txt`. Every run writes the matrix as it saw it, with the counters each probe moved and any ICMP error the kernel's rate limits held back (`OutRateLimitGlobal`, `OutRateLimitHost`), to `matrix.observed.txt` beside the rendered rulesets.

To add a row, add the line under its scenario; when it needs a service that is not there yet, add the port to `GW_SERVE`, `WAN_SERVE` or `TV_SERVE` in `vnet.py`, and add a line to `test_every_service_a_row_expects_blocked_answers_the_gateway_itself` so the row's refusal means something.

## Other interface names

The settings name the gateway's ports (`TV_IF`, `WAN_IF`, `VPN_IF`; [design decision 24](../../docs/design-decisions.md#24-the-tv-side-comes-from-the-settings-file)), and nothing in `tvgw-apply` or the guard may assume the defaults. `TVGW_VIRTUAL_IFNAMES` chooses the names the gateway namespace's three interfaces get:

| Value | TV port | Uplink | Tunnel | What the conf says |
|---|---|---|---|---|
| unset or `default` | `eth0` | `wlan0` | `tun0` | `WAN_IF=wlan0` only: `TV_IF` and `VPN_IF=auto` are the script's own defaults |
| `alt` | `tvport0` (a name a `.link` file gives a USB adapter) | `uplink0` | `wg0` | `TV_IF=tvport0`, `WAN_IF=uplink0`, `VPN_IF=wg0` |

No name of the second set is one the script falls back to, so a place that ignored a setting fails a row: the netdev table would hook a port that does not exist, a route would leave by the wrong interface, the tunnel's drop would miss `wg0`. Any other value stops the run when `vnet.py` is imported. The scratch namespace of `tvgw-apply --check` gets the same names; the TV's own end of its cable is `eth0` in both, since it is the TV's name, not the gateway's. The matrix's verdicts `pass:wlan0` and `pass:tun0` name the uplink and the tunnel whatever they are called. A test on the shared gateway names its ports as `vnet.TV_IF`, `vnet.WAN_IF` and `vnet.VPN_IF`, never as `eth0`, `wlan0` or `tun0` written out, which tests/unit/test_virtual_harness.py checks. CI's `virtual` job runs the suite once with each value on `ubuntu-latest`, and `virtual-arm64` runs it with the default names on `ubuntu-24.04-arm`.

## Running it

It needs Linux, root, `nft`, `ip`, `unshare`, `mount` and `bash`; `conntrack` is optional (without it the re-apply test does not compare conntrack entries), and so is `tcpdump` (without it the in-path module skips its contrast with the passive feeder). (inpath) The in-path module needs a kernel with `nfnetlink_queue` and `nft_queue`, which CI's workflow loads by name; without them it skips, or fails under `TVGW_VIRTUAL_REQUIRED=1`, and so do the `DNSGATE_FILL=inpath` variants of the rulesets. Without them every test is skipped; with `TVGW_VIRTUAL_REQUIRED=1`, as CI sets it, a missing one is an error instead. It takes about a minute and a half; the guard's module probes two dozen closed ports four times, each silent for half a second.

In a Linux VM (a Multipass, Lima or UTM Ubuntu guest works; the suite never needs the VM's own network):

```sh
sudo apt-get install -y nftables iproute2 conntrack tcpdump python3-venv
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
sudo env PYTHONDONTWRITEBYTECODE=1 TVGW_VIRTUAL_ARTIFACTS=/tmp/virtual \
    .venv/bin/python -m pytest -m virtual tests/virtual -p no:cacheprovider -rxX
ls /tmp/virtual                  # rulesets/, scenarios/, services/, matrix.observed.txt
```

In a privileged container, on a workstation with Docker (Docker Desktop's kernel has conntrack built in and the container has no `/lib/modules`, so `modprobe` is replaced by a no-op):

```sh
docker run --rm --privileged -v "$PWD":/src:ro -w /src ubuntu:24.04 sh -c '
  apt-get update -qq && apt-get install -y -qq python3-pytest python3-yaml nftables iproute2 conntrack >/dev/null &&
  ln -sf /bin/true /usr/local/sbin/modprobe &&
  PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python3 -m pytest -m virtual tests/virtual -p no:cacheprovider -rxX'
```

To include the resolver tests, fetch the release this tvgw pins with its own code, which checks the SHA-256 and unpacks it, on the Linux machine or in the container that runs the suite: the check runs the binary, and the download needs `ca-certificates`. It prints the binary's path; pass it as `TVGW_VIRTUAL_ADGUARD=<path>` through `sudo env` with the other variables.

```sh
python3 -c 'import sys; from tvgw import aghinstall; print(aghinstall.fetch_release(sys.argv[1]))' "$(mktemp -d)"
```

`test_virtual_adguard_listen.py` also needs `TVGW_VIRTUAL_HOST_NET=1` and a stub on 127.0.0.53, so it skips in a plain container.

Use `debian:trixie` in place of `ubuntu:24.04` for the nftables release the reference gateway runs (1.1.3); `ubuntu-latest` in CI has 1.0.9. The suite also runs on the gateway itself without harm, since its namespaces and mounts are its own, but there is no reason to.

## Artifacts

`TVGW_VIRTUAL_ARTIFACTS` names the directory (a pytest temporary directory when unset). CI uploads it as `virtual-gateway`, `virtual-gateway-alt` and `virtual-gateway-arm64`, one per run, kept 30 days.

| Path | What it is |
|---|---|
| `rulesets/<variant>.nft` | What `tvgw-apply --check` printed for one variant: the rulesets it would load (four, five with `CAPTURE_MODE=headers`; one fewer with `DNSGATE=off`). `nft -c -f` reads each on its own. |
| `scenarios/<name>/` | `apply.log`, the files the apply wrote under `/run/tvgw` (`ruleset.applied`, `settings.applied`, the counter listings) and `ruleset.nft`, the gateway namespace's whole ruleset after the apply. |
| `services/<namespace>.log` | Each stand-in service's stderr. |
| `adguard/` | (lists) The YAML the plan wrote (`AdGuardHome.planned.yaml`), the binary's `--check-config` output and the YAML as AdGuard left it (`AdGuardHome.after.yaml`); AdGuard's own log is `services/adguard.log`. |
| `matrix.observed.txt` | The matrix as the run saw it, with every probe's moved counters, and `# expected ...` on a row that failed. |

## Cleaning up

Everything the suite creates is named `tvgwv-<pid>-<role>`, and the listen test's dummy interface `tvgwv-d<n>`. The session fixture kills the services and deletes the namespaces on any exit pytest sees, including a failure or Ctrl-C, and `atexit` covers one it does not. A run killed with `kill -9` leaves its namespaces behind; the next run deletes every `tvgwv-` namespace whose process is gone, and CI's workflow deletes any that remain in an `always()` step. By hand:

```sh
for ns in $(ip netns list | awk '{print $1}' | grep '^tvgwv-'); do sudo ip netns del "$ns"; done
for dev in $(ip -o link show | awk -F': ' '{print $2}' | grep '^tvgwv-'); do sudo ip link del "$dev"; done
```

A killed run can also leave the empty mount points it created; `sudo rmdir /etc/tvgw /var/lib/tvgw /run/tvgw` removes them where no gateway is installed.
