# Deployment

This folder holds everything that runs on the Pi outside the Python package: the installer, the settings template, and the configs, units and scripts in the folders below. This page owns how a change reaches the gateway, what `install.sh` does, and the settings file; it is for whoever installs the gateway, deploys a change, or edits anything here. How the pieces fit together is in [the architecture page](../docs/architecture.md). The .deb carries this folder as `/usr/lib/tvgw/deploy` and its postinst runs the same `install.sh` ([packaging](../docs/packaging.md)).

## How a change reaches the gateway

A change reaches the Pi one of two ways, and both end in the same installer. Run `make gate` first either way: it is ruff check, ruff format check and the unit tests, exactly what CI's test job runs.

**From your workstation.** `make deploy PI=<ssh-host>` copies the working tree to a staging copy in the ssh user's home on the Pi, `~/tvgw-deploy/`, with `rsync -a --delete --exclude-from=deploy/rsync.exclude`, then runs `sudo tvgw-deploy/deploy/sync-install.sh` over ssh. That script takes `/run/tvgw/install.lock` (waiting up to 600 seconds), copies the staging tree to `/opt/tvgw/src` with the same `rsync` options, and runs `install.sh` there with the lock handed down on descriptor 8 (`TVGW_INSTALL_LOCKED=1`). The copy includes uncommitted changes, and `--delete` removes files on the Pi that the tree no longer has. Because the lock covers the copy into `/opt/tvgw/src` as well as the install, a `make deploy` can never replace the tree under a running CI install or suite, nor a CI run under it. `PI` defaults to the contents of `.pi` in the checkout, a file git ignores. `make hardware` runs the suite under the same lock (`flock -w 600 /run/tvgw/install.lock`).

**From GitHub.** `.github/workflows/ci.yml` runs on four events:

| Event | Jobs that run |
|---|---|
| A push to `main` that changes a file outside `**/*.md` and `docs/**` | `test`, then `hardware` |
| A push to `main` that changes only files matching `**/*.md` or `docs/**` | none (`paths-ignore`) |
| A pull request | `test` |
| A manual run (`workflow_dispatch`) | `test` and `mutation` |
| The schedule, Monday 06:17 UTC | `mutation` |

The jobs:

- **`test`** runs on `ubuntu-latest` for Python 3.11, the floor (Debian 12), and 3.13, the gateway's interpreter (Debian 13). It installs the checkout with `pip install -e ".[dev]"` and runs `make gate`. Its concurrency group is per ref and per Python version with `cancel-in-progress: true`, so a newer push replaces an older unit run.
- **`hardware`** needs `test` and runs only for push events in the upstream repository, never a fork's. It runs on the self-hosted runner on the Pi (labels `self-hosted` and `tvgw`). One step runs `sudo deploy/sync-install.sh env PYTHONDONTWRITEBYTECODE=1 /opt/tvgw-venv/bin/python -m pytest -m hardware tests/hardware ...` from the checkout, as root because earlier suite runs leave root-owned `__pycache__` directories in `/opt/tvgw/src`: under the install lock it copies the checkout there with the same `rsync` options, runs `install.sh`, then the hardware suite, with `PYTHONDONTWRITEBYTECODE=1` as the only variable handed to root ([hardware tests](../tests/hardware/README.md)).
- **`mutation`** runs `mutmut run` and `mutmut results` on Python 3.13 ([mutation testing](../tests/unit/README.md#mutation-testing)).

`.github/workflows/virtual.yml` is a second workflow, on every pull request and on the same pushes to `main`: as root on `ubuntu-latest`, it loads `tvgw-apply` into a network-namespace copy of the gateway, checks every ruleset variant with `nft -c` and probes the result against the reachability matrix ([the virtual gateway](../tests/virtual/README.md)). On a pull request it runs before anything is merged; on a push to `main` it runs beside the `hardware` job, which does not wait for it.

The deploy is never cut short, because `install.sh` is a linear `set -e` script with no rollback:

- The workflow has no top-level `concurrency` key, since a cancel there would reach the deploy.
- The `hardware` job's group is `deploy-tvgw` with `cancel-in-progress: false`: a running deploy is never cancelled, and a newer push waits for it.
- The job's timeout is 90 minutes: the first analyze run can use its whole start timeout ([the units](systemd/README.md#units)), and the suite runs ingest twice.

The workflow's permissions are `contents: read`. Every action is pinned by commit hash with its version in a comment, and `.github/dependabot.yml` proposes the bumps weekly. `tests/unit/test_deploy_lint.py` fails `make gate` when the workflow gains a top-level `concurrency` key, when the deploy group may cancel or the timeout drops under 90 minutes, when the Markdown filter or an action's pin goes, when a step hands root the runner's whole environment with `sudo -E`, when `make deploy` and CI stop sharing `rsync.exclude`, or when a write of `/opt/tvgw/src`, an install or a suite run does not hold the install lock.

A push to `main` is therefore a deploy. `install.sh` ends with `exec tvgw verify`, so verify's verdict is the exit status of `make deploy` and of the CI deploy step.

## What install.sh does

`install.sh` runs with `set -euo pipefail`, so a failing command stops it with nothing after it done. A deliberate stop prints `tvgw: <reason>` and exits 1, and an `ERR` trap makes any other failing command exit 1 too, whatever its own status: nmcli's 3 and 4, for one, would otherwise read as the two exits kept for the .deb's postinst. Those are 75, the TV is not identified and there is no terminal to ask on (step 10), and 76, under the postinst only, the install completed and `tvgw verify` reported a `FAIL` (step 20). The steps, in order:

1. **Lock and AdGuard Home.** Creates `/run/tvgw` and takes `/run/tvgw/install.lock`, waiting up to 600 seconds (10 minutes). It stops with `another install is running` after that. Under `sync-install.sh` the lock is already held, from before the copy that replaced the tree, and handed down on descriptor 8 (`TVGW_INSTALL_LOCKED=1`), so `make deploy` and a CI deploy never interleave: neither can copy into `/opt/tvgw/src` while the other installs or runs the suite. Then, before it writes anything else, it stops unless AdGuard Home is installed at `/opt/AdGuardHome/AdGuardHome` and reports at least `v0.107.73`, `tvgw verify`'s floor, and prints the command that installs it ([design decision 25](../docs/design-decisions.md#25-adguard-home-is-a-checked-dependency-never-bundled)).
2. **Directories, user and modes.** Creates `/etc/tvgw`, `/var/log/tvgw`, `/var/lib/tvgw` and `/var/lib/tvgw/pcap`, and the system user `tvgw-pcap` (group `nogroup`, no home, no login shell) when it is missing. It then stops, before any unit is installed, unless `/usr/bin/dumpcap` exists and `tvgw-pcap` can execute it (`runuser -u tvgw-pcap -- test -x`), with `/usr/bin/dumpcap is missing or not executable by tvgw-pcap: ...` ([what dumpcap needs](../docs/capture.md#what-dumpcap-needs)). It sets owners and modes on the directories and on the logs, pcaps, store, pairing key, TV readings, DoH list and reports that exist, as listed in [where it lives and who can read it](../docs/privacy-and-retention.md#where-it-lives-and-who-can-read-it).
3. **Settings files.** Copies `tvgw.conf.example` to `/etc/tvgw/tvgw.conf` and `nftables/block4.txt` to `/etc/tvgw/block4.txt`, each only when missing. It sets the settings file's group and mode on every run, and copies `nftables/doh-exclude.txt` to `/etc/tvgw/` on every run.
4. **Settings check.** Sources the settings file and fills the defaults `install.sh` itself uses ([the settings file](#the-settings-file)). It stops unless the TV side passes the `tvgw-net` checks it shares with `tvgw-apply` ([the TV side](#the-tv-side)): `TV_IF` is an interface name other than `WAN_IF`, `lo` and `tun0`; `TV_NET` is a private IPv4 network from `/16` to `/27`; `GW_IP` is a host address in it outside the DHCP pool; `TV_IP` is a host address in it other than `GW_IP`. It also stops unless `TV_NAME` is 1 to 63 letters, digits, `-` and `_`, `URL_FILTER_RESOLVER` is an IPv4 address, and no address of `WAN_IF` lies in a network that overlaps `TV_NET`. These values go into the dnsmasq, nginx and NetworkManager files through `sed`, so they are refused before those files are written. A `TV_MAC` that is missing, malformed or the template's `00:00:00:00:00:00` is not a stop: it means the TV is unknown (step 10).
5. **Package.** Creates the virtualenv `/opt/tvgw-venv` when it has no Python. From a checkout, it upgrades pip, removes the checkout's `build/` (setuptools never prunes `build/lib` and the rsync exclude list protects it from `--delete`, so a module deleted from `src/` would keep shipping), and installs the checkout with the `lgwebos` and `analyst` extras plus `pytest` (the hardware suite runs on the Pi). From the .deb, which it recognizes by `requirements.lock` and `wheels/` beside its tree, it checks the wheelhouse against `SHA256SUMS`, then installs offline: the dependencies with `pip install --no-index --require-hashes -r requirements.lock` and the tvgw wheel itself. Either way it links `/usr/local/bin/tvgw`. The install is not editable, so the gateway runs the profile inside the package, not the files in `/opt/tvgw/src`.
6. **Scripts.** Installs `tvgw-apply`, `tvgw-doh-update` and `tvgw-analyze` into `/usr/local/sbin/`.
7. **Legacy cleanup.** Removes the retired text-report pipeline (`/usr/local/sbin/tvgw-extract`, the TSV files, the copied query log, `/var/lib/tvgw/archive`, the old brief files) and the retired `/usr/local/sbin/tvgw-prune`. Once, marked by `reports/.from-the-store`, it moves the reports written before the store into `reports/legacy/`.
8. **Configs and units.** Writes `/etc/dnsmasq.d/tvgw.conf` from the template, with the TV side filled in and the pin line left out while the TV is unknown ([DHCP for the TV](dnsmasq/README.md)). Writes the NetworkManager config with `TV_IF` filled in, installs the dispatcher, the logrotate config, the kernel switches (`/etc/sysctl.d/60-tvgw.conf`, [the kernel switches](sysctl/README.md)), and every unit and timer, and writes the capture's drop-in `tvgw-pcap.service.d/tv-side.conf` with `TV_IF`, `TV_NET` and `GW_IP`. Then the guard ([design decision 42](../docs/design-decisions.md#42-guard-the-pi-is-closed-to-the-tv-whatever-nftables-holds)): it renders `nftables/guard.nft.template` with `TV_IF`, `TV_NET` and `GW_IP` into `/etc/tvgw/guard.nft`, stops if `nft -c` rejects it, enables `tvgw-guard.service`, and reloads it (or starts it, when it is not active) only when the file changed, the table is missing, or the live table differs from the listing the unit left in `/run/tvgw/guard.applied` (a hole a killed `tvgw discover` left behind, or a hand edit), so a deploy keeps the guard's counters. Then `tvgw guard cotenants` writes `IPAddressDeny=TV_NET` drop-ins for the units `CO_TENANT_UNITS` names that are installed and removes the ones no longer wanted, followed by `systemctl daemon-reload` and no restart. systemd is expected to attach a running unit's new filter on that reload (the reading in [design decision 42](../docs/design-decisions.md#42-guard-the-pi-is-closed-to-the-tv-whatever-nftables-holds)); the hardware suite checks it with `bpftool`, and otherwise the filter takes effect at the unit's next restart. `tvgw guard avahi` adds `TV_IF` to avahi's `deny-interfaces`, keeping a one-time backup, and restarts avahi when it changed; the line it adds under its own comment follows `TV_IF` and comes out again when `avahi-daemon` leaves `CO_TENANT_UNITS`, while a name appended to a list you wrote stays. All of this comes before `tv-lan` is brought up, so the Pi is closed to the TV before the TV side exists.
9. **The TV interface.** Reloads NetworkManager's config and creates the `tv-lan` connection on `TV_IF` with `GW_IP/<prefix>` when it does not exist. When it exists with another interface or address (`TV_IF`, `TV_NET` or `GW_IP` changed), it prints `tvgw: tv-lan moves to ...`, turns off autoconnect on the other profiles of the new port as a first install does, modifies `tv-lan` and brings it up again; otherwise it brings it up only when it is not already active ([the TV interface](networkmanager/README.md)).
10. **Finding the TV.** When the TV is unknown, restarts dnsmasq (with its hardening and health check, step 18) so the TV gets a pool address. With a terminal, it runs `tvgw discover --write` until it succeeds, and stops if you decline to retry. Without a terminal, or under the .deb's postinst (`TVGW_POSTINST=1`), it prints the two commands to run, `sudo tvgw discover --write` and then the installer again, and exits 75. After discovery it reads the settings again, stops unless `TV_MAC`, `TV_IP` and `TV_NAME` now pass, and writes the dnsmasq file with the pin.
11. **nginx**, when installed. Writes both nginx files with `__RESOLVER__` replaced by `URL_FILTER_RESOLVER` and `__GW_IP__` by `GW_IP`, adds `include /etc/nginx/tvgw/stream.conf;` to `/etc/nginx/nginx.conf` once, and removes `/etc/nginx/sites-enabled/default`. Then it runs `nginx -t`, and stops when nginx rejects the config, with the old one still live. Then it writes the drop-in `nginx.service.d/tvgw.conf`: the start order and `Restart=on-failure`, then the sandbox in `nginx/tvgw-hardening.conf`, with `MemoryDenyWriteExecute=yes` only when `nginx -T` shows no `pcre_jit on` and `AF_INET6` only when it shows a `listen [` address. When the drop-in is unchanged and nginx is running it reloads nginx, which keeps the TLS passthrough and downloads in progress. When the drop-in changed, it restarts nginx once, since a sandbox applies only at a start, and checks that nginx is active and listening on `GW_IP:80` and `GW_IP:443`. If not, it prints a `WARNING`, writes the drop-in again without the sandbox and restarts nginx. Once nginx serves that way it records the refused sandbox in `/var/lib/tvgw/.unit-stamps/nginx-refused`, so the next deploy does not try it again; if nginx still does not serve, the fault is not the sandbox, the install stops, and no stamp is left. Without nginx it prints a note and skips the step.
12. **AdGuard Home**, when `/opt/AdGuardHome/AdGuardHome.yaml` exists. Writes the drop-in `AdGuardHome.service.d/workdir.conf`, reloads systemd and runs `tvgw adguard apply`; a failed apply stops the install. Before AdGuard's first-run wizard has run, it prints a reminder instead.
13. **nftables.service.** Masks the stock unit unless it is enabled, because its `flush ruleset` would wipe the VPN client's tables and the gateway's. A failure to mask does not stop the install.
14. **The DoH list.** When `/var/lib/tvgw/doh4.txt` is missing or empty, starts `tvgw-doh-update.service` once, which fetches the list and runs `tvgw-apply`. When that fails, as it does offline, it prints a note and goes on.
15. **Enable the firewall unit.** Enables `tvgw.service`; a failure stops the install.
16. **Analyst schedules.** Renders `ANALYST_SCHEDULE` and `ANALYST_WEEKLY_SCHEDULE` into the drop-ins `tvgw-analyst.timer.d/schedule.conf` and `tvgw-analyst-weekly.timer.d/schedule.conf`. `HH:MM` becomes `*-*-* HH:MM:00`, `Day HH:MM` becomes `Day *-*-* HH:MM:00`, `hourly` stays `hourly`, and any other value is passed as written. `systemd-analyze calendar` must accept each, or the install stops. Then it runs `sync`: everything the next boot reads is on disk, so a power cut right after a deploy cannot leave `tvgw-apply` or a unit empty (`install` writes each as a new file, which ext4 may hold in memory for half a minute).
17. **The firewall.** When `tvgw.service` is active, runs `tvgw-apply` in place instead of restarting the unit, because a restart runs the stop path first and turns forwarding off ([stopping](nftables/README.md#stopping)). Otherwise it starts the unit with `systemctl restart`.
18. **Services.** Restarts dnsmasq with the hardening drop-in `dnsmasq.service.d/20-tvgw-hardening.conf` (no `CAP_NET_ADMIN` or `CAP_NET_RAW` in its bounding set, which the template's `dhcp-broadcast` and `no-ping` make possible; [DHCP for the TV](dnsmasq/README.md#the-hardening-drop-in)), then checks that dnsmasq is active and holds UDP 67. If not, it prints a `WARNING`, removes the drop-in and restarts dnsmasq without it; the TV never loses DHCP to a hardening line. Once dnsmasq serves that way the drop-in is recorded as refused in `/var/lib/tvgw/.unit-stamps/dnsmasq-refused`. If dnsmasq still does not serve, the install stops, as a failed restart did before, and leaves no stamp, so the drop-in is tried again once the other fault is fixed. Then it runs `systemctl enable --now` for `tvgw-flowlog`, `tvgw-pcap`, `tvgw-dnsgate` and the eight timers. `enable --now` does not restart a running unit, so it then restarts each of `tvgw-pcap`, `tvgw-flowlog` and `tvgw-dnsgate` whose inputs changed since its last restart here: its unit file, for the capture also `TV_IF`, `TV_NET` and `GW_IP`, `tvgw-pcap-headers.service` and the `CAPTURE_MODE` line, for the flow log also `TV_IP`, for the DNS-gate feeder also the settings file and the package it runs. A hash of those inputs is kept per unit in `/var/lib/tvgw/.unit-stamps/` and written after the restart, so a restart an earlier run did not reach (it stopped on the way) happens on the next. Every restart is a short hole in the evidence, so an unchanged unit is left alone.
19. **First runs.** Starts `tvgw-analyze.service` once, and `tvgw-backup.service` only when `/var/lib/tvgw/backup/` holds no `tvgw-*.db` yet: the timer makes the daily copies, and a copy on every deploy would crowd them out. A failure prints a message and does not stop the install.
20. **Verdict.** Prints the installed version, then runs `exec tvgw verify`. Its exit status is the installer's, so any `FAIL` fails the deploy ([what tvgw verify checks](../docs/troubleshooting.md#what-tvgw-verify-checks)). Under the .deb's postinst it runs `tvgw verify` and exits 76 on a `FAIL`, which the postinst reports without failing the package ([design decision 23](../docs/design-decisions.md#23-the-deb-runs-installsh)).

### What is idempotent

Run `install.sh` as often as you like. It keeps `/etc/tvgw/tvgw.conf` and `/etc/tvgw/block4.txt`, reuses the virtualenv, creates `tv-lan` and the nginx include only once, and moves the legacy reports only once. It re-applies the firewall without a restart. `tvgw adguard apply` changes nothing, and does not restart AdGuard, when the config already matches. The DoH list is fetched, and the first backup taken, only when missing.

A re-run does disturb these:

- nginx reloads; downloads in progress continue. It restarts once instead when its drop-in changed (a new sandbox).
- dnsmasq restarts.
- The guard reloads only when `/etc/tvgw/guard.nft` changed or the table is missing; then its counters start again from zero.
- AdGuard Home restarts when its config changed, and the TV's lookups fail for those seconds.
- The firewall re-apply resets every rule's counters; `tvgw-apply`'s listings either side of the reload, stored by the next `tvgw verify --record`, keep the brief's counts whole ([design decision 13](../docs/design-decisions.md#13-counters-not-logs-prove-the-firewall-held)).
- A long-running unit restarts when its file, or what it read at start, changed. What ends or passes in that moment is not recorded, and that hour's pcap is split in two.
- `/etc/tvgw/doh-exclude.txt` and the two analyst timer drop-ins are written again. Make local edits in the repository.
- `tvgw-analyze` runs once more.

## The settings file

`/etc/tvgw/tvgw.conf` holds the gateway's site settings, one `KEY=value` per line. It is site-specific: never commit a real one.

Two kinds of reader see it, and they read it differently:

- **Python** reads it with `config.parse_conf` in src/tvgw/config.py. It takes `KEY=value`, `KEY="value"` and `KEY='value'`, drops a trailing `# comment`, and ignores any other line. It refuses an unquoted value with a space in it, which the shell would run as a command, so both readers see the same file. It reads only the keys in `config.CONF_KEYS`, so a misspelt key is ignored. An empty value keeps the default, a missing file means every default, and a file that exists but cannot be read is an error. `config.load` checks the values; a bad one makes every `tvgw` command print `tvgw: <KEY>=<value> in tvgw.conf: <reason>` and exit 1.
- **The shell scripts** source the file with `.`, so it must also be valid shell. Quote a value that contains a space: unquoted, its second word runs as a command, and under `set -e` that stops `install.sh`, `tvgw-apply` and `tvgw-doh-update`. `tvgw-apply` and `install.sh` fill their own defaults with `${KEY:=value}`; `tests/unit/test_deploy_lint.py` keeps `tvgw-apply`'s defaults and accepted values equal to `config.Settings` and `config.CHOICES`.

Every key, in the order of `config.CONF_KEYS`, then the three keys only the shell side reads:

| Key | Default | Read by | Meaning | After a change |
|---|---|---|---|---|
| `TV_IP` | `10.10.10.17` | `install.sh`, `tvgw-apply`, `tvgw-flowlog.service`, Python | The TV's fixed address, pinned by DHCP. Every source keeps only the rows from it. `install.sh` requires an address in `10.10.10.0/24`. Once `TV_MAC` is known, `tvgw-apply` forwards only from this address (and, until the TV's lease moves to it, from the address its older lease names) ([the forward chain](nftables/README.md#forward)). | Re-run `install.sh`: `tvgw-flowlog` and `tvgw-dnsgate` read it when they start, and the installer restarts both when it changed (step 18), and re-applies the firewall. |
| `TV_MAC` | empty; the template holds `00:00:00:00:00:00` | `install.sh`, `tvgw-apply`, Python | The TV's wired MAC, for the DHCP pin and AdGuard's client entry. Missing, malformed or the placeholder means the TV is unknown, and `tvgw discover --write` fills it in. A usable one also switches on `tvgw-apply`'s forward pin to `TV_IP`. | Re-run `install.sh`. |
| `TV_NAME` | `tv` | `install.sh`, Python | The DHCP host name and AdGuard's client name: 1 to 63 letters, digits, `-` and `_`. | Re-run `install.sh`. |
| `GW_IP` | `10.10.10.1` | `install.sh`, `tvgw-apply`, Python | The gateway's address on the TV subnet: the firewall's DNS redirect and input rules, the DHCP router and DNS option, nginx's listeners, `tv-lan`'s address, the generated `$dnsrewrite` rules, `tvgw verify`'s resolver checks, `tvgw discover` and the DNS gate feeder. ### The TV side

`TV_IF`, `TV_NET` and `GW_IP` describe the gateway's TV port, and every file that needs them reads them from the settings file, with `eth0`, `10.10.10.0/24` and `10.10.10.1` as the defaults ([design decision 24](../docs/design-decisions.md#24-the-tv-side-comes-from-the-settings-file)). A second site with another port or subnet edits the settings and re-runs `install.sh`; no script changes.

| Where | What it takes from the settings |
|---|---|
| `tvgw-apply` | `TV_IF` in every rule that names the TV interface, the forwarding switch and the IPv6 guard; `TV_NET` in the source check, the masquerade, rule 60 and the gate; `GW_IP` in the DNS redirect, the input rules and the gate; the broadcast address derived from `TV_NET`. |
| `install.sh` | The checks above, the `tv-lan` connection, and the generated dnsmasq, nginx and NetworkManager files. |
| dnsmasq template | `TV_IF`, `GW_IP`, the pool (the 10th to 20th host of `TV_NET`) and the netmask. |
| nginx files | `GW_IP` in both `listen` lines. |
| NetworkManager | `TV_IF` in `90-tvgw.conf` and in the dispatcher's interface match. |
| `tvgw.service` | The stop path's `forwarding=0`: the `TV_IF` of the last apply (`/run/tvgw/settings.applied`), else the settings'. |
| The guard | `TV_IF`, `TV_NET` and `GW_IP` in `/etc/tvgw/guard.nft`, rendered by `install.sh` from `nftables/guard.nft.template`; `TV_NET` in the co-tenants' drop-ins and dnsmasq's `IPAddressAllow`. |
| `tvgw-pcap.service` | `TV_IF`, `TV_NET` and `GW_IP` in dumpcap's interface and filter, from the drop-in `tvgw-pcap.service.d/tv-side.conf` that `install.sh` writes; systemd reads it as root, since the capture user cannot read the settings file. |
| Python | `config.Settings` and `config.tv_side`, which applies the same rules as the shell's `tvgw-net` block. |

`install.sh` and `tvgw-apply` share the `tvgw-net` block byte for byte, and `tests/unit/test_tv_side.py` runs it and `config.tv_side` on the same cases. `tvgw-apply` refuses a TV side that fails them before it loads anything, so a subnet such as `0.0.0.0/0`, which would masquerade and route by table 100 everything the Pi forwards, never reaches nft. Changing `TV_IF` takes a re-run of `install.sh`, which moves `tv-lan`. Until then the TV is never forwarded unfiltered: `tvgw-apply` stops when `GW_IP` is on another interface than `TV_IF`, the forward chain drops the TV subnet on any other port before it accepts non-TV traffic, masquerade covers only what came in on `TV_IF`, and the previous apply's port stops forwarding once the new one is filtered ([the order of operations](nftables/README.md#order-of-operations)). `config.load` checks only the shape of `TV_IF` and `TV_NET`; the membership rules are checked where the values are written, so a reader such as `tvgw brief` still works on a settings file the installer would refuse.

After changing `TV_NET`, power-cycle the TV (or unplug and replug its cable) once the install is done. A TV still holding a lease from the old subnet renews by broadcast from its old address, and the source rules (the guard's and `inet tvgw`'s input chain, and dnsmasq's `IPAddressAllow`) drop a source outside `TV_NET` before the DHCP accept, so dnsmasq never sends the `DHCPNAK` that would move it. A link change makes the TV ask again from `0.0.0.0`, which is let through; without one it recovers only when the old lease expires. Accepting a renewal from outside `TV_NET` would mean opening dnsmasq's address filter to every source, which is not worth one power-cycle.

## Gotchas

- The template's `WAN_GW` line is an example. Replace it with the router's address.
- Everything follows `TV_IF`, `TV_NET` and `GW_IP` ([the TV side](#the-tv-side)), the capture through the drop-in `install.sh` writes. `STATE_DIR` moves only the Python side.
- `install.sh` stops at the first failing step, and nothing after it runs: a failed `tvgw adguard apply` leaves the firewall un-reapplied and the units unrestarted. A unit restart it did not reach is made by the next run, since the record of what each long-running unit started with is written only after its restart. It exits non-zero after a complete run too, when the final `tvgw verify` has a `FAIL`. A stop exits 1 whatever the failing command returned (an `ERR` trap), so the two deliberate statuses, 75 and 76, always mean what [the package's postinst](../docs/packaging.md#how-installsh-tells-the-two-apart) reads them as.
- `tvgw adguard apply` run by hand uses the profile inside the installed package, not the files in `/opt/tvgw/src`. A policy change needs a deploy.
- `make deploy` copies uncommitted changes, and `--delete` removes files on the Pi that your tree lacks.
- The NetworkManager dispatcher and `tvgw-doh-update` both run `tvgw-apply`, so either can bring the TV back online after you stop `tvgw.service` by hand.
- `install.sh` skips `tvgw adguard apply` until AdGuard's first-run wizard has written `/opt/AdGuardHome/AdGuardHome.yaml`; run it by hand afterwards.
