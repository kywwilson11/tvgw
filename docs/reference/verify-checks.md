# What tvgw verify checks

This page owns every check `sudo tvgw verify` runs: what each one proves, what its `FAIL` or `WARN` means, and the first thing to do about it. It is for anyone reading verify's output, from the end of an install to the timer's journal, and the pages that act on a check link to its row here.

## How it runs

`sudo tvgw verify` runs the checks below in this order and prints one line for each: `OK`, `WARN` or `FAIL`, the check's name, and a detail (`check` in `src/tvgw/verify.py`). A FAIL fails the command ([exit codes](commands.md)). A WARN is a check that passed and wants a look; it fails nothing, no unit and no deploy, and `--json` marks it `"warn": true`. Each command a check runs has a 30-second timeout, and a command that fails or times out reads as empty. A detail never names the home: an address outside `TV_NET` reads `<lan address>`, `<public address>` or `<router>`, a MAC `<mac>`, a USB adapter `usb-ethernet-<n>`, and the host, TV and Wi-Fi names their own placeholders, because verify's output ends every deploy's public CI log ([what the hardware job prints](../../deploy/README.md#what-the-hardware-job-prints)). Read the value itself on the gateway with the command the check names.

`tvgw-verify.timer` runs it with `--record`, which also stores the verdict and a snapshot of every firewall counter for the brief ([design decision 13](../design-decisions.md#13-counters-not-logs-prove-the-firewall-held)). A run that cannot be stored prints `tvgw verify: could not record the run: <error>` to stderr and fails as well.

Each run also replaces `/run/tvgw/status.txt` with one line: `ok <epoch> <n>`, the run's time in seconds since 1970 and the number of checks it ran, or `fail <epoch> <names>`, the names of the checks that failed, in run order. A WARN counts as passed, as it does in the exit status. The line holds check names only, never a detail, because a detail can name an interface, an address or a host, and every account may read the file ([where it lives](../how-it-works/privacy-and-retention.md#where-it-lives-and-who-can-read-it)). It is written whole, as a temporary file renamed over the old one (`write_status` in src/tvgw/verify.py). A run that cannot write it keeps its verdict and its exit status: as root it prints `tvgw verify: could not write /run/tvgw/status.txt: <error>` to stderr, and without root it leaves the last root run's file in place and says nothing.

## The checks

| Check | Runs when | What it proves | What a FAIL means | What to do |
|---|---|---|---|---|
| `ruleset` | Always | Table `inet tvgw` is loaded and holds the key rules in `KEY_RULES`: the DNS DNAT to the gateway, the DoT/DoQ reject, the DoH set, the home-LAN set, masquerade and the invalid-state drop. With `BLOCK_QUIC=yes` it must also hold the QUIC reject (`QUIC_RULE`). | `table inet tvgw is not loaded`: either the service is stopped (the TV is dark) or the table was deleted by hand (the TV may be forwarded with no filter; `forwarding` says which). `missing: <rules>`: a key rule is gone. | If `tvgw.service` is inactive, run `sudo systemctl start tvgw`; otherwise run `sudo tvgw-apply` and read its error. A rule still missing after a clean apply means `tvgw-apply` and `KEY_RULES` disagree, which `tests/unit/test_deploy_lint.py` exists to catch. |
| `ruleset_unchanged` | The table is loaded | The live ruleset, without counters, equals what `tvgw-apply` last wrote to `/run/tvgw/ruleset.applied`. | `differs from the last apply`: someone changed the rules by hand, or something else rewrote them. `no baseline: ... missing (run tvgw-apply)`: the table is loaded but its listing is gone, so nothing vouches for the rules. | Run `sudo tvgw-apply`. |
| `applied_current` | The table is loaded and the baseline exists | No input of `tvgw-apply` (`/etc/tvgw/tvgw.conf`, `/etc/tvgw/block4.txt`, `/var/lib/tvgw/doh4.txt`) changed after the last successful apply, unless the change is under `APPLY_GRACE = 120` seconds old. The grace covers `tvgw-doh-update`'s write-then-apply and an edit in progress. For the settings file only the keys `tvgw-apply` reads count (`APPLY_KEYS`: `UPLINK`, `WAN_IF`, `WAN_GW`, `BLOCK_QUIC`, `STRICT_PORTS`, `DNSGATE`, `TV_IF`, `TV_NET`, `GW_IP`, `CAPTURE_MODE`, `VPN_IF`, `ADTECH_PORT_WALL`, and `TV_IP` and `TV_MAC`, which set the forward pin), with defaults filled in, compared with what the last apply recorded in `/run/tvgw/settings.applied`: an edit to the TV's identity, retention or the analyst needs no apply. Without that record (an apply from before it was kept) any edit counts. | `changed after the last apply: <files>`: an input changed and no apply has succeeded since. A `block4.txt` line nft rejects leaves the old set loaded and the baseline unchanged, so this is the only check that sees it. So is a firewall setting changed in the conf and never applied. | Run `sudo tvgw-apply` and read its error. |
| `forwarding` | Always | `net.ipv4.ip_forward` is 1, and so is the `forwarding` switch of the TV interface and of the uplink (`WAN_IF`, or with `UPLINK=vpn` the tunnel `VPN_IF` names or finds, `tun0` before one exists). | Forwarding is off and the TV is offline: the service is stopped, was never applied, or was restarted the way that once left the TV dark ([incidents](../incidents.md)). The detail names each switch that is off. | If `tvgw.service` is inactive, run `sudo systemctl start tvgw`; otherwise run `sudo tvgw-apply`, which writes all three switches. |
| `ipv6_off` | Always | `disable_ipv6` is 1 on the TV interface. | IPv6 could reach the TV. | Run `sudo tvgw-apply`. |
| `ipv6_guard` | Always | Table `netdev tvgw_l2` is loaded and holds the rule commented `no IPv6 from the TV`, which drops every IPv6 frame on the TV interface at the wire. | `netdev tvgw_l2 is not dropping IPv6 on eth0`: the table was deleted by hand, or `tvgw-apply` could not load it and only warned, which it does while `eth0` is down. `disable_ipv6` still drops IPv6, so this is the second wall, and the source of the brief's IPv6 line in Firewall held. | Check that `eth0` is up (`ip link show eth0`), then run `sudo tvgw-apply` and read its warning. |
| `tv_route` | Always | A packet from `TV_IP` entering on the TV interface routes out the chosen uplink (`ip route get 1.1.1.1 from <TV_IP> iif eth0`). | `via nothing`: no route, and the TV is dark. `via <device>`: the TV's traffic would leave the wrong way. | Check that the uplink is up, then run `sudo tvgw-apply`. The NetworkManager dispatcher runs it again when the uplink comes back. |
| `policy_rule` | `UPLINK=direct` | `ip rule` priority 60 sends the TV subnet to table 100. | The TV may take the VPN's routes. | Check that the uplink is up, then run `sudo tvgw-apply`. |
| `vpn_dnat_idle` | Always | No packet reached the VPN client's split-DNS DNAT chain, a chain with `fwdsplitdns` in its name. With no such chain the check passes with `no VPN DNAT chain present`. | `<N> TV DNS packets reached the VPN's DNAT`: TV DNS met the VPN client's redirect before tvgw's, a bypass of AdGuard. The counter is the VPN client's, so the FAIL stays until that chain is reloaded. | Run `sudo tvgw-apply` so that the `pre_nat` chain is in place ([the firewall](../../deploy/nftables/README.md)). The FAIL clears once the VPN client reloads its chain and the counter starts from zero. |
| `doh4_loaded` | Always | The DoH block set covers at least `MIN_DOH_ADDRESSES = 50` addresses, counted through the prefixes and ranges nft merges them into. | The set is empty or short, so the firewall's DoH block is thin. | Run `sudo systemctl start tvgw-doh-update` and read `journalctl -u tvgw-doh-update`. |
| `doh4_fresh` | Always | `/var/lib/tvgw/doh4.txt` was written less than `DOH_MAX_AGE` (8 days) ago. | The daily update has not replaced the list for over a week, or the file is missing (`doh4.txt missing`). | `journalctl -u tvgw-doh-update` says why: the download failed, the list had under 50 entries, or `doh-exclude.txt` is missing. `systemctl list-timers tvgw-doh-update.timer` shows whether the timer runs. |
| `resolver_rewrite` | Always | Each URL-filter host resolves through AdGuard to exactly `GW_IP`. | `<host>-><answer>`: the `$dnsrewrite` rules are missing or AdGuard is down, so the URL filter is bypassed or the file service is unreachable. | Run `sudo tvgw adguard diff`, then `sudo tvgw adguard apply`. |
| `resolver_must_allow` | Always | Each must-allow host resolves to at least one address other than `0.0.0.0`. | `<host>->no answer`: the resolver did not reply. `blocked`: it answered `0.0.0.0`. `empty answer`: NXDOMAIN, REFUSED, SERVFAIL or no A record, which another blocking mode or an upstream outage gives. | For `blocked`, act as the must-allow red line says ([red lines](../use/daily-brief.md#red-lines)). For `no answer`, run `systemctl status AdGuardHome`. For `empty answer`, check that the gateway reaches the DoH upstreams, then run `sudo tvgw adguard diff`. |
| `services` | Always | These units are active (`SERVICES`): `AdGuardHome`, `dnsmasq`, `nginx`, `tvgw`, `tvgw-pcap` (`tvgw-pcap-headers` in its place with `CAPTURE_MODE=headers`), `tvgw-flowlog`, the eight timers `tvgw-analyze`, `tvgw-prune`, `tvgw-doh-update`, `tvgw-verify`, `tvgw-backup`, `tvgw-analyst`, `tvgw-analyst-weekly` and `tvgw-autoblock`, and `tvgw-dnsgate` unless `DNSGATE=off`. | `down: <units>`. A timer that is not active never fires. | Run `systemctl status <unit>` and `journalctl -u <unit>`, and see [failed units](../use/troubleshooting.md#failed-units). Start a stopped timer with `sudo systemctl enable --now <timer>`. |
| `tv_paths` | Always | The last hourly TV reading (`tvcheck.txt`) says the TV's Wi-Fi and Wi-Fi Direct are `disconnected` and its tethering is off (`reading_paths` in src/tvgw/verify.py; the keys are `PATH_KEYS` in src/tvgw/lgwebos.py). No reading, or a reading without those keys, passes with a detail saying so: verify cannot tell a TV that is off from one whose firmware never answers the question. | `second path: <paths> (read <time>)`: the TV reports a way to a network around the gateway. | On the TV: Settings > Network: Wi-Fi off, saved network deleted, Wi-Fi Direct off. Then `sudo tvgw tvcheck`. The brief carries the same as a red line. |
| `adguard_version` | Always | `AdGuardHome --version`, run beside `AdGuardHome.yaml`, reports at least `ADGUARD_MIN`, v0.107.79, the release with the 2026 DoH and DoQ fixes (0.107.78 removed h2c and tightened DoH upstream validation; 0.107.79 fixed a DoQ resource exhaustion). With `--record` the version goes to the store, and the brief shows it in Coverage. | `<version> is below v0.107.79, ...`: the resolver on the TV segment has a known hole. `could not read it from <path> --version`: the binary is there but printed no version. `AdGuard Home is not installed (<path> missing); install it natively ...`: no binary beside the config at all; AdGuard Home is a checked dependency that tvgw never bundles ([design decision 25](../design-decisions.md#25-adguard-home-is-a-checked-dependency-never-bundled)). | Install AdGuard Home with the command the line prints, or download the new release and run `sudo tvgw adguard upgrade <its AdGuardHome binary>` ([upgrading AdGuard Home](../how-it-works/adguard.md#upgrading-adguard-home)), then run `sudo tvgw verify` again. |
| `list_sentinels` | Always | (lists) Each subscribed HaGeZi list's sentinel name resolves to `0.0.0.0` through AdGuard (`SENTINELS` in src/tvgw/verify.py: `h4g3z1-pro.web.app`, `h4g3z1-native-lgwebos.web.app`, `h4g3z1-doh.web.app`), so every list is loaded and not empty ([the sentinels](../how-it-works/adguard.md#the-sentinels)). A list with no known sentinel is not checked. | `list not in force: <sentinel>-><answer>`: AdGuard answered the sentinel with an address (the list was emptied by its last download, or never loaded) or did not answer. | `sudo head -3 /opt/AdGuardHome/data/filters/*.txt` and `sudo wc -l` on the same files show which list is short. `journalctl -u AdGuardHome` says why a download failed. If every list file looks whole, HaGeZi may have renamed the sentinel: a false alarm, not an outage. |
| `adguard_pinned` | Always | (lists) `systemctl show -P ExecStart AdGuardHome` carries `--no-check-update`, and so does the running process (`/proc/<MainPID>/cmdline`, when there is one to read), so AdGuard never replaces its own binary ([the service runs with --no-check-update](../how-it-works/adguard.md#the-service-never-updates-itself)). | `AdGuard Home may update itself`: the drop-in is missing or was not applied. `the running AdGuard Home (pid <N>) was started without --no-check-update`: systemd has the drop-in, but AdGuard was not restarted into it. `could not read AdGuardHome's ExecStart`: systemd knows no such unit. | Run `sudo tvgw adguard service`; it prints what it did, or why it put the old unit back. |
| `dnsgate` | `DNSGATE` is not `off` | Table `inet tvgw_gate` holds the set `resolved4` and the rule commented `TV to an address DNS never returned`. The detail gives the set's size; an empty set is not a FAIL, because verify cannot tell a feeder that hears nothing from a TV that is off. A WARN when the set holds more than half its size (`GATE_FULL`): `<N> of <size> addresses in the set, over 50%: what is the TV resolving?`. The set holds a day of the TV's distinct answers, and a full set loses addresses. | `missing: set` or `missing: counting rule`: the gate table is gone or partial. | Run `sudo tvgw-apply`, which builds the gate table with `DNSGATE=count` and prints `tvgw: DNS gate table not loaded` when it cannot. For the WARN, `tvgw sql "select qname, count(*) from dns where t > strftime('%s','now','-1 day') group by 1 order by 2 desc limit 20"` shows what the TV asked most. |
| `capture` | Always | The capture unit `CAPTURE_MODE` does not pick is not active, and with `CAPTURE_MODE=headers` table `inet tvgw_capture` holds the rule commented `capture: the first packets of each TV connection` ([the capture](../how-it-works/capture.md#checking-it)). The detail names the mode and its unit. | `<unit> is running with CAPTURE_MODE=<mode>`: both captures write the pcap directory and every hello is counted twice. `inet tvgw_capture has no capture rule`: the headers capture runs and records nothing. | For the first, `sudo systemctl restart tvgw-pcap`, which lets only the right unit run. For the second, `sudo tvgw-apply` and read its warning. |
| `guard_present` | Always | Table `inet tvgw_guard` is loaded, its `input`, `forward` and `output` chains hook their own hook at priority `filter + 10`, it holds the rules in `guard.KEY_RULES` (the final input drop, the spoofed-source and weak-host drops, the home-LAN forward drop, the TV-API rule), and, when `tvgw-guard.service` left its listing in `/run/tvgw/guard.applied`, the live table equals it ([the guard](../../deploy/nftables/README.md#the-guard)). | `table inet tvgw_guard is not loaded`: the gateway is open to the TV whenever `inet tvgw` is absent. `missing: <chains or rules>`: the table is partial. `differs from what tvgw-guard loaded`: changed by hand, or `tvgw discover`'s hole is in it for the length of a search. | `sudo systemctl reload-or-restart tvgw-guard`, then `journalctl -u tvgw-guard`. If `/etc/tvgw/guard.nft` is missing, re-run `install.sh`. |
| `guard_quiet` | Always | While `inet tvgw` is loaded, the guard's final input counter (`guard: TV may not reach other Pi services`) has not grown since `tvgw-apply` listed it right after its last load (`/run/tvgw/counters.after-apply`). A WARN, never a FAIL: the guard did its job. | `WARN guard_quiet: <n> packets inet tvgw accepted were dropped by the guard since the last apply`: `inet tvgw`'s input chain let through something the guard refuses, so the two disagree. | `sudo nft list chain inet tvgw input` and `sudo nft list chain inet tvgw_guard input`, side by side; then `sudo tvgw-apply`. |
| `cotenants_denied` | Always | Every unit `CO_TENANT_UNITS` names that is loaded, every active socket unit of one of them, and every loaded `qbittorrent-nox@` instance carries `IPAddressDeny` covering `TV_NET`, as `systemctl show` reports it (so a drop-in never daemon-reloaded counts as missing). A WARN when one does not. | `WARN cotenants_denied: no IPAddressDeny=<TV_NET>: <units>`: that service relies on nftables alone to keep the TV out. | Re-run `install.sh`, which writes the drop-ins (`tvgw guard cotenants`) and reloads systemd. |
| `dnsmasq_caps` | Always | The running dnsmasq's effective capabilities (`CapEff` in `/proc/<pid>/status`) hold neither `net_admin` nor `net_raw`, and neither does its bounding set (`CapBnd`); the detail decodes `CapEff`. A WARN when either does. | `WARN dnsmasq_caps: ... holds net_admin` (or `net_raw`): `dhcp-broadcast` (or `no-ping`) is missing from the dnsmasq config, so dnsmasq kept the capability after its privilege drop and a DHCP-parser bug could rewrite the firewall. `WARN dnsmasq_caps: ... bounding set keeps net_admin and net_raw: the hardening drop-in is not in place`: `install.sh` took the drop-in out because dnsmasq would not serve with it, or it was never written; `CapEff` alone cannot show this, since with both config lines dnsmasq drops every capability with or without the drop-in. | `systemctl cat dnsmasq`, `ls /var/lib/tvgw/.unit-stamps/dnsmasq-refused`, and `journalctl -u dnsmasq` for the start that failed ([the hardening drop-in](../../deploy/dnsmasq/README.md#the-hardening-drop-in)). |
| `flowlog_events` | Always | The flow log hears the TV ([design decision 43](../design-decisions.md#43-the-flow-log-hears-the-tv-alone-and-the-gates-day-starts-at-each-answer)): `nf_conntrack_events` is `0` and the `ct_events` rule is in `inet tvgw`, and `tvgw-flowlog`'s main process (or a child of it) holds a conntrack event socket, found through `/proc/<pid>/fd` and the `Inode` column of `/proc/net/netlink` (protocol 12, non-zero `Groups`). The detail gives the socket's `Drops`, the events the kernel could not queue to it since the logger started; with `--record` they go into `fw_counters` as `flowlog: event socket drops`, and the ingest warns when they grew. A WARN when the switch is not `0`: the flow log works, but every connection on the gateway reaches its socket again. | `nf_conntrack_events=0 and no ct_events rule: the flow log records nothing`: the rule is gone (a hand edit, or a rollback to an older `tvgw-apply`). `tvgw-flowlog has no running process`, `holds no conntrack event socket`: the logger is down or not listening. `cannot read /proc/<pid>/fd (run as root)`. | For the first, `sudo tvgw-apply`; after a rollback, `sudo sysctl -w net.netfilter.nf_conntrack_events=2` ([rolling back the code](../project/deploying.md#rolling-back-the-code)). For the others, `systemctl status tvgw-flowlog` and `journalctl -u tvgw-flowlog -n 20`. For the WARN, `sudo tvgw-apply`. |

## In plain words

Each check also has three short plain texts for a reader who is not an engineer: what it means, what you notice on the TV, and the fix (`PLAIN` in src/tvgw/verify.py). `GROUPS` sorts the checks under five plain sentences, listed below in their order. `SETTLING` names the checks that can fail for a few minutes after an install or a restart, while the blocklists download and the services start, and then pass on their own: `list_sentinels`, `doh4_loaded`, `doh4_fresh`, `services`, `capture`, `flowlog_events` and `resolver_must_allow`. tests/unit/test_verify_plain.py fails when a check has no plain entry or no group, when a fix names a command or a unit this version does not have, and when the list or the table below differs from the code.

- the TV's cable leads to the internet only through this computer: `ruleset`, `ruleset_unchanged`, `applied_current`, `forwarding`, `ipv6_off`, `ipv6_guard`, `tv_route`, `policy_rule`, `guard_present`, `guard_quiet`, `cotenants_denied`, `dnsmasq_caps`
- the TV's lookups go through the filter: `vpn_dnat_idle`, `resolver_rewrite`, `resolver_must_allow`, `list_sentinels`, `doh4_loaded`, `doh4_fresh`, `adguard_version`, `adguard_pinned`, `dnsgate`
- recording what the TV does: `capture`, `flowlog_events`
- every service is running: `services`
- the TV has no second way out: `tv_paths`

| Check | What it means | What you notice | The fix |
|---|---|---|---|
| `ruleset` | The gateway's firewall is not loaded, or one of its main rules is missing. | Usually the TV has no internet. If the firewall was removed by hand, the TV may be online unfiltered. | Run `sudo systemctl start tvgw`, then `sudo tvgw-apply`, and read any error it prints. |
| `ruleset_unchanged` | The firewall rules were changed after the gateway last set them. | Nothing on the TV, unless the change lets something through. | Run `sudo tvgw-apply`. It sets the gateway's own rules again. |
| `applied_current` | A firewall setting or list was changed, and the gateway has not put the change in force. | Nothing on the TV: the rules from before the change still hold. | Run `sudo tvgw-apply`, and read any error it prints. |
| `forwarding` | The gateway is not passing the TV's traffic on to the internet. | The TV has no internet. | Run `sudo systemctl start tvgw`, then `sudo tvgw-apply`. |
| `ipv6_off` | IPv6, the newer kind of internet address, is switched on for the TV's port. The gateway handles only the older kind, so IPv6 must stay off there. | Nothing on the TV. One of the two walls against IPv6 is down. | Run `sudo tvgw-apply`. |
| `ipv6_guard` | The second wall against IPv6 on the TV's port is missing. The first, IPv6 switched off, still holds. | Nothing on the TV. | Check that the TV's cable is plugged in and the TV is on, then run `sudo tvgw-apply`. It cannot add this wall while the TV's port is down. |
| `tv_route` | The TV's traffic has no way out to the internet, or would leave by the wrong connection. | The TV has no internet. | Check that the gateway itself is online, then run `sudo tvgw-apply`. It also runs on its own when the gateway's connection comes back. |
| `policy_rule` | The rule that sends the TV's traffic out by the gateway's direct connection is missing. | The TV's traffic may leave by another route, such as a VPN on the gateway. | Check that the gateway itself is online, then run `sudo tvgw-apply`. |
| `vpn_dnat_idle` | Some of the TV's lookups reached the VPN program's own redirect instead of the filter. | Nothing on the TV. Those lookups were not filtered. | Run `sudo tvgw-apply`. The check passes again once the VPN program reloads its rules, which starts its count from zero. |
| `doh4_loaded` | The list of encrypted lookup services the TV may not use is empty or too short. | Nothing on the TV, but it could look names up around the filter. | Run `sudo systemctl start tvgw-doh-update`, then check again with `sudo tvgw verify`. If it still fails, see why with `journalctl -u tvgw-doh-update -n 20`. |
| `doh4_fresh` | That list of encrypted lookup services has not been updated for over a week, or is missing. | Nothing on the TV. Services added to the list since then are not blocked. | Run `sudo systemctl start tvgw-doh-update`. If it fails, see why with `journalctl -u tvgw-doh-update -n 20`. |
| `resolver_rewrite` | The filter does not send the TV's requests for its maker's file service to the gateway's web filter. | App installs and updates may fail, or those requests go out unchecked. | Run `sudo tvgw adguard apply`, then check again with `sudo tvgw verify`. |
| `resolver_must_allow` | A name the TV needs, such as its clock or its app store, is blocked or gets no answer. | The TV may show the wrong time or certificate errors, apps may not load, or it may say it has no internet. | Right after setup or a restart, wait 5 minutes and check again with `sudo tvgw verify`. If it still fails, check that the gateway is online, then run `sudo tvgw adguard apply`. |
| `services` | One of the gateway's programs or scheduled jobs is not running. Its name is on this check's line in the output of `sudo tvgw verify`. | It depends on which. If tvgw itself or the filter stopped, the TV has no internet. If the program that gives the TV its address stopped, the TV loses the internet the next time it asks for an address. If a scheduled job stopped, the brief stops updating. | Start it with `sudo systemctl start <name>`, or for a name ending in .timer, `sudo systemctl enable --now <name>`. Then see why it stopped with `journalctl -u <name> -n 20`. |
| `tv_paths` | The TV reports a second connection, such as Wi-Fi or Wi-Fi Direct, that goes around the gateway. | Nothing on the TV. Whatever it sends that way is neither filtered nor recorded. | On the TV, switch Wi-Fi off, forget every saved network, and switch off Wi-Fi Direct and any tethering. Then see what the TV reports now with `sudo tvgw tvcheck`. This check clears with the next hourly reading. |
| `adguard_version` | The filter (AdGuard Home) is missing, older than the release with the 2026 security fixes, or does not say which version it is. | If it is missing, the TV gets no answers to its lookups. If it is old, it has a known security hole. | Install or update it with the command on this check's line in the output of `sudo tvgw verify`, then check again with `sudo tvgw verify`. If the line names no command, ask for help on the project's issue tracker. |
| `list_sentinels` | The filter has not loaded one of its blocklists, or a list arrived empty. | Nothing on the TV. The trackers on that list are not refused. | Right after setup, wait 5 minutes: the lists may still be downloading. Then check again with `sudo tvgw verify`. If it still fails, see why a download failed with `journalctl -u AdGuardHome -n 50`. |
| `adguard_pinned` | The filter (AdGuard Home) could replace itself with a new version that tvgw has not checked. | Nothing on the TV. | Run `sudo tvgw adguard service`. |
| `dnsgate` | The gateway's count of connections to addresses the TV never looked up is missing. A warning instead says its list is more than half full. | Nothing on the TV. Without the count, the brief cannot show those connections. | Run `sudo tvgw-apply`. A warning alone needs no fix: the TV, or the program that fills the list, is doing something new. |
| `capture` | The recording of the TV's traffic is set up wrong: two recorders run at once, or the one in use receives nothing. | Nothing on the TV. The brief counts some connections twice, or the recording stays empty. | Run `sudo systemctl restart tvgw-pcap`, then `sudo tvgw-apply`. |
| `guard_present` | The gateway's second firewall, which keeps the TV away from this computer's own services, is missing or changed. | Nothing on the TV. If the main firewall also goes, the TV could reach this computer's other services. | Run `sudo systemctl reload-or-restart tvgw-guard`. |
| `guard_quiet` | The second firewall stopped traffic from the TV that the main firewall let through: the two disagree. | Nothing on the TV: the second firewall held. | Run `sudo tvgw-apply`. If the warning comes back, ask for help on the project's issue tracker. |
| `cotenants_denied` | Another program on this computer is kept from the TV only by the firewall, not also by a setting of its own. | Nothing on the TV. | Run the installer again, which adds that setting: `sudo /usr/lib/tvgw/deploy/install.sh` (from a source checkout, `sudo deploy/install.sh`). |
| `dnsmasq_caps` | The program that gives the TV its address kept a permission it does not need, one that could change the firewall. | Nothing on the TV. | Run the installer again: `sudo /usr/lib/tvgw/deploy/install.sh` (from a source checkout, `sudo deploy/install.sh`). If the warning stays, ask for help on the project's issue tracker. |
| `flowlog_events` | The gateway's log of the TV's connections is not recording, or it hears every connection on this computer instead of the TV's alone. | Nothing on the TV. The brief misses connections, or the log can lose some when this computer is busy. | Run `sudo tvgw-apply`, then `sudo systemctl start tvgw-flowlog`. Check again with `sudo tvgw verify`: this check needs root. |

## The refused stamps

When dnsmasq or nginx will not serve with its hardening, `install.sh` prints a `WARNING`, takes the hardening out, and records the refused text in `/var/lib/tvgw/.unit-stamps/dnsmasq-refused` or `nginx-refused`, so later deploys run that daemon unhardened instead of restarting it twice each time, until the hardening text itself changes ([what install.sh does](../../deploy/README.md#what-installsh-does), steps 11 and 18). Each later deploy prints `WARNING: ... runs unhardened`. After a deploy, on the gateway:

```sh
sudo ls /var/lib/tvgw/.unit-stamps/ | grep refused   # must print nothing
```

A stamp is a finding: read the daemon's journal from the deploy that wrote it for why it would not start. Once the cause is fixed, delete the stamp and re-run `install.sh`, which tries the hardening again with its health check.
