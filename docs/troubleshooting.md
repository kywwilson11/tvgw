# Troubleshooting

This page takes a symptom to its cause and its fix: the TV misbehaves, a unit failed, `tvgw verify` fails, or the brief looks wrong. It owns what each verify check proves and every warning that ingest and pcap retention print; red-line actions and longer procedures are in the [operations runbook](operations.md).

## Start here

`tvgw verify` says within seconds whether the firewall, routing, resolver and services hold, so start there. Then look for failed units, then at the brief's Coverage line.

On the Pi:

1. Run `sudo tvgw verify`. Each line starts with `OK`, `WARN` or `FAIL`, then the check's name and a detail; a WARN fails nothing and wants a look ([what a WARN is](#what-tvgw-verify-checks)). Look each FAIL up in [what tvgw verify checks](#what-tvgw-verify-checks).
2. If every line is `OK`, run `systemctl --failed`. Look a listed unit up in [failed units](#failed-units).
3. If no unit failed, run `tvgw brief` and read Coverage. A source marked `NOT ASSESSED`, or an `ingest warning:` line, leads to [ingest warnings](#ingest-warnings).
4. If all of that is clean, start from the symptom in [the TV](#the-tv).

```sh
sudo tvgw verify      # one OK, WARN or FAIL line per check
systemctl --failed    # must list nothing
tvgw brief            # read Coverage first
```

A `RED LINE:` in the brief has its action in [red lines](operations.md#red-lines). Each unit's journal is in [reading the journals](../deploy/systemd/README.md#reading-the-journals).

## What tvgw verify checks

`sudo tvgw verify` runs the checks below in this order and prints one line for each: `OK`, `WARN` or `FAIL`, the check's name, and a detail (`check` in `src/tvgw/verify.py`). A FAIL fails the command ([exit codes](../src/tvgw/README.md#commands)). A WARN is a check that passed and wants a look; it fails nothing, no unit and no deploy, and `--json` marks it `"warn": true`. Each command a check runs has a 30-second timeout, and a command that fails or times out reads as empty.

`tvgw-verify.timer` runs it with `--record`, which also stores the verdict and a snapshot of every firewall counter for the brief ([design decision 13](design-decisions.md#13-counters-not-logs-prove-the-firewall-held)). A run that cannot be stored prints `tvgw verify: could not record the run: <error>` to stderr and fails as well.

Each run also replaces `/run/tvgw/status.txt` with one line: `ok <epoch> <n>`, the run's time in seconds since 1970 and the number of checks it ran, or `fail <epoch> <names>`, the names of the checks that failed, in run order. A WARN counts as passed, as it does in the exit status. The line holds check names only, never a detail, because a detail can name an interface, an address or a host, and every account may read the file ([where it lives](privacy-and-retention.md#where-it-lives-and-who-can-read-it)). It is written whole, as a temporary file renamed over the old one (`write_status` in src/tvgw/verify.py). A run that cannot write it keeps its verdict and its exit status: as root it prints `tvgw verify: could not write /run/tvgw/status.txt: <error>` to stderr, and without root it leaves the last root run's file in place and says nothing.

| Check | Runs when | What it proves | What a FAIL means | What to do |
|---|---|---|---|---|
| `ruleset` | Always | Table `inet tvgw` is loaded and holds the key rules in `KEY_RULES`: the DNS DNAT to the gateway, the DoT/DoQ reject, the DoH set, the home-LAN set, masquerade and the invalid-state drop. With `BLOCK_QUIC=yes` it must also hold the QUIC reject (`QUIC_RULE`). | `table inet tvgw is not loaded`: either the service is stopped (the TV is dark) or the table was deleted by hand (the TV may be forwarded with no filter; `forwarding` says which). `missing: <rules>`: a key rule is gone. | If `tvgw.service` is inactive, run `sudo systemctl start tvgw`; otherwise run `sudo tvgw-apply` and read its error. A rule still missing after a clean apply means `tvgw-apply` and `KEY_RULES` disagree, which `tests/unit/test_deploy_lint.py` exists to catch. |
| `ruleset_unchanged` | The table is loaded | The live ruleset, without counters, equals what `tvgw-apply` last wrote to `/run/tvgw/ruleset.applied`. | `differs from the last apply`: someone changed the rules by hand, or something else rewrote them. `no baseline: ... missing (run tvgw-apply)`: the table is loaded but its listing is gone, so nothing vouches for the rules. | Run `sudo tvgw-apply`. |
| `applied_current` | The table is loaded and the baseline exists | No input of `tvgw-apply` (`/etc/tvgw/tvgw.conf`, `/etc/tvgw/block4.txt`, `/var/lib/tvgw/doh4.txt`) changed after the last successful apply, unless the change is under `APPLY_GRACE = 120` seconds old. The grace covers `tvgw-doh-update`'s write-then-apply and an edit in progress. For the settings file only the keys `tvgw-apply` reads count (`APPLY_KEYS`: `UPLINK`, `WAN_IF`, `WAN_GW`, `BLOCK_QUIC`, `STRICT_PORTS`, `DNSGATE`, `TV_IF`, `TV_NET`, `GW_IP`, `CAPTURE_MODE`, `VPN_IF`, `ADTECH_PORT_WALL`, and `TV_IP` and `TV_MAC`, which set the forward pin), with defaults filled in, compared with what the last apply recorded in `/run/tvgw/settings.applied`: an edit to the TV's identity, retention or the analyst needs no apply. Without that record (an apply from before it was kept) any edit counts. | `changed after the last apply: <files>`: an input changed and no apply has succeeded since. A `block4.txt` line nft rejects leaves the old set loaded and the baseline unchanged, so this is the only check that sees it. So is a firewall setting changed in the conf and never applied. | Run `sudo tvgw-apply` and read its error. |
| `forwarding` | Always | `net.ipv4.ip_forward` is 1, and so is the `forwarding` switch of the TV interface and of the uplink (`WAN_IF`, or with `UPLINK=vpn` the tunnel `VPN_IF` names or finds, `tun0` before one exists). | Forwarding is off and the TV is offline: the service is stopped, was never applied, or was restarted the way that once left the TV dark ([incidents](incidents.md)). The detail names each switch that is off. | If `tvgw.service` is inactive, run `sudo systemctl start tvgw`; otherwise run `sudo tvgw-apply`, which writes all three switches. |
| `ipv6_off` | Always | `disable_ipv6` is 1 on the TV interface. | IPv6 could reach the TV. | Run `sudo tvgw-apply`. |
| `ipv6_guard` | Always | Table `netdev tvgw_l2` is loaded and holds the rule commented `no IPv6 from the TV`, which drops every IPv6 frame on the TV interface at the wire. | `netdev tvgw_l2 is not dropping IPv6 on eth0`: the table was deleted by hand, or `tvgw-apply` could not load it and only warned, which it does while `eth0` is down. `disable_ipv6` still drops IPv6, so this is the second wall, and the source of the brief's IPv6 line in Firewall held. | Check that `eth0` is up (`ip link show eth0`), then run `sudo tvgw-apply` and read its warning. |
| `tv_route` | Always | A packet from `TV_IP` entering on the TV interface routes out the chosen uplink (`ip route get 1.1.1.1 from <TV_IP> iif eth0`). | `via nothing`: no route, and the TV is dark. `via <device>`: the TV's traffic would leave the wrong way. | Check that the uplink is up, then run `sudo tvgw-apply`. The NetworkManager dispatcher runs it again when the uplink comes back. |
| `policy_rule` | `UPLINK=direct` | `ip rule` priority 60 sends the TV subnet to table 100. | The TV may take the VPN's routes. | Check that the uplink is up, then run `sudo tvgw-apply`. |
| `vpn_dnat_idle` | Always | No packet reached the VPN client's split-DNS DNAT chain, a chain with `fwdsplitdns` in its name. With no such chain the check passes with `no VPN DNAT chain present`. | `<N> TV DNS packets reached the VPN's DNAT`: TV DNS met the VPN client's redirect before tvgw's, a bypass of AdGuard. The counter is the VPN client's, so the FAIL stays until that chain is reloaded. | Run `sudo tvgw-apply` so that the `pre_nat` chain is in place ([the firewall](../deploy/nftables/README.md)). The FAIL clears once the VPN client reloads its chain and the counter starts from zero. |
| `doh4_loaded` | Always | The DoH block set covers at least `MIN_DOH_ADDRESSES = 50` addresses, counted through the prefixes and ranges nft merges them into. | The set is empty or short, so the firewall's DoH block is thin. | Run `sudo systemctl start tvgw-doh-update` and read `journalctl -u tvgw-doh-update`. |
| `doh4_fresh` | Always | `/var/lib/tvgw/doh4.txt` was written less than `DOH_MAX_AGE` (8 days) ago. | The daily update has not replaced the list for over a week, or the file is missing (`doh4.txt missing`). | `journalctl -u tvgw-doh-update` says why: the download failed, the list had under 50 entries, or `doh-exclude.txt` is missing. `systemctl list-timers tvgw-doh-update.timer` shows whether the timer runs. |
| `resolver_rewrite` | Always | Each URL-filter host resolves through AdGuard to exactly `GW_IP`. | `<host>-><answer>`: the `$dnsrewrite` rules are missing or AdGuard is down, so the URL filter is bypassed or the file service is unreachable. | Run `sudo tvgw adguard diff`, then `sudo tvgw adguard apply`. |
| `resolver_must_allow` | Always | Each must-allow host resolves to at least one address other than `0.0.0.0`. | `<host>->no answer`: the resolver did not reply. `blocked`: it answered `0.0.0.0`. `empty answer`: NXDOMAIN, REFUSED, SERVFAIL or no A record, which another blocking mode or an upstream outage gives. | For `blocked`, act as the must-allow red line says ([red lines](operations.md#red-lines)). For `no answer`, run `systemctl status AdGuardHome`. For `empty answer`, check that the Pi reaches the DoH upstreams, then run `sudo tvgw adguard diff`. |
| `services` | Always | These units are active (`SERVICES`): `AdGuardHome`, `dnsmasq`, `nginx`, `tvgw`, `tvgw-pcap` (`tvgw-pcap-headers` in its place with `CAPTURE_MODE=headers`), `tvgw-flowlog`, the eight timers `tvgw-analyze`, `tvgw-prune`, `tvgw-doh-update`, `tvgw-verify`, `tvgw-backup`, `tvgw-analyst`, `tvgw-analyst-weekly` and `tvgw-autoblock`, and `tvgw-dnsgate` unless `DNSGATE=off`. | `down: <units>`. A timer that is not active never fires. | Run `systemctl status <unit>` and `journalctl -u <unit>`, and see [failed units](#failed-units). Start a stopped timer with `sudo systemctl enable --now <timer>`. |
| `tv_paths` | Always | The last hourly TV reading (`tvcheck.txt`) says the TV's Wi-Fi and Wi-Fi Direct are `disconnected` and its tethering is off (`reading_paths` in src/tvgw/verify.py; the keys are `PATH_KEYS` in src/tvgw/lgwebos.py). No reading, or a reading without those keys, passes with a detail saying so: verify cannot tell a TV that is off from one whose firmware never answers the question. | `second path: <paths> (read <time>)`: the TV reports a way to a network around the gateway. | On the TV: Settings > Network: Wi-Fi off, saved network deleted, Wi-Fi Direct off. Then `sudo tvgw tvcheck`. The brief carries the same as a red line. |
| `adguard_version` | Always | `AdGuardHome --version`, run beside `AdGuardHome.yaml`, reports at least `ADGUARD_MIN`, v0.107.79, the release with the 2026 DoH and DoQ fixes (0.107.78 removed h2c and tightened DoH upstream validation; 0.107.79 fixed a DoQ resource exhaustion). With `--record` the version goes to the store, and the brief shows it in Coverage. | `<version> is below v0.107.79, ...`: the resolver on the TV segment has a known hole. `could not read it from <path> --version`: the binary is there but printed no version. `AdGuard Home is not installed (<path> missing); install it natively ...`: no binary beside the config at all; AdGuard Home is a checked dependency that tvgw never bundles ([design decision 25](design-decisions.md#25-adguard-home-is-a-checked-dependency-never-bundled)). | Install AdGuard Home with the command the line prints, or download the new release and run `sudo tvgw adguard upgrade <its AdGuardHome binary>` ([upgrading AdGuard Home](adguard.md#upgrading-adguard-home)), then run `sudo tvgw verify` again. |
| `list_sentinels` | Always | (lists) Each subscribed HaGeZi list's sentinel name resolves to `0.0.0.0` through AdGuard (`SENTINELS` in src/tvgw/verify.py: `h4g3z1-pro.web.app`, `h4g3z1-native-lgwebos.web.app`, `h4g3z1-doh.web.app`), so every list is loaded and not empty ([the sentinels](adguard.md#the-sentinels)). A list with no known sentinel is not checked. | `list not in force: <sentinel>-><answer>`: AdGuard answered the sentinel with an address (the list was emptied by its last download, or never loaded) or did not answer. | `sudo head -3 /opt/AdGuardHome/data/filters/*.txt` and `sudo wc -l` on the same files show which list is short. `journalctl -u AdGuardHome` says why a download failed. If every list file looks whole, HaGeZi may have renamed the sentinel: a false alarm, not an outage. |
| `adguard_pinned` | Always | (lists) `systemctl show -P ExecStart AdGuardHome` carries `--no-check-update`, and so does the running process (`/proc/<MainPID>/cmdline`, when there is one to read), so AdGuard never replaces its own binary ([the service runs with --no-check-update](adguard.md#the-service-runs-with---no-check-update)). | `AdGuard Home may update itself`: the drop-in is missing or was not applied. `the running AdGuard Home (pid <N>) was started without --no-check-update`: systemd has the drop-in, but AdGuard was not restarted into it. `could not read AdGuardHome's ExecStart`: systemd knows no such unit. | Run `sudo tvgw adguard service`; it prints what it did, or why it put the old unit back. |
| `dnsgate` | `DNSGATE` is not `off` | Table `inet tvgw_gate` holds the set `resolved4` and the rule commented `TV to an address DNS never returned`. The detail gives the set's size; an empty set is not a FAIL, because verify cannot tell a feeder that hears nothing from a TV that is off. A WARN when the set holds more than half its size (`GATE_FULL`): `<N> of <size> addresses in the set, over 50%: what is the TV resolving?`. The set holds a day of the TV's distinct answers, and a full set loses addresses. | `missing: set` or `missing: counting rule`: the gate table is gone or partial. | Run `sudo tvgw-apply`, which builds the gate table with `DNSGATE=count` and prints `tvgw: DNS gate table not loaded` when it cannot. For the WARN, `tvgw sql "select qname, count(*) from dns where t > strftime('%s','now','-1 day') group by 1 order by 2 desc limit 20"` shows what the TV asked most. |
| `capture` | Always | The capture unit `CAPTURE_MODE` does not pick is not active, and with `CAPTURE_MODE=headers` table `inet tvgw_capture` holds the rule commented `capture: the first packets of each TV connection` ([the capture](capture.md#checking-it)). The detail names the mode and its unit. | `<unit> is running with CAPTURE_MODE=<mode>`: both captures write the pcap directory and every hello is counted twice. `inet tvgw_capture has no capture rule`: the headers capture runs and records nothing. | For the first, `sudo systemctl restart tvgw-pcap`, which lets only the right unit run. For the second, `sudo tvgw-apply` and read its warning. |
| `guard_present` | Always | Table `inet tvgw_guard` is loaded, its `input`, `forward` and `output` chains hook their own hook at priority `filter + 10`, it holds the rules in `guard.KEY_RULES` (the final input drop, the spoofed-source and weak-host drops, the home-LAN forward drop, the TV-API rule), and, when `tvgw-guard.service` left its listing in `/run/tvgw/guard.applied`, the live table equals it ([the guard](../deploy/nftables/README.md#the-guard)). | `table inet tvgw_guard is not loaded`: the Pi is open to the TV whenever `inet tvgw` is absent. `missing: <chains or rules>`: the table is partial. `differs from what tvgw-guard loaded`: changed by hand, or `tvgw discover`'s hole is in it for the length of a search. | `sudo systemctl reload-or-restart tvgw-guard`, then `journalctl -u tvgw-guard`. If `/etc/tvgw/guard.nft` is missing, re-run `install.sh`. |
| `guard_quiet` | Always | While `inet tvgw` is loaded, the guard's final input counter (`guard: TV may not reach other Pi services`) has not grown since `tvgw-apply` listed it right after its last load (`/run/tvgw/counters.after-apply`). A WARN, never a FAIL: the guard did its job. | `WARN guard_quiet: <n> packets inet tvgw accepted were dropped by the guard since the last apply`: `inet tvgw`'s input chain let through something the guard refuses, so the two disagree. | `sudo nft list chain inet tvgw input` and `sudo nft list chain inet tvgw_guard input`, side by side; then `sudo tvgw-apply`. |
| `cotenants_denied` | Always | Every unit `CO_TENANT_UNITS` names that is loaded, every active socket unit of one of them, and every loaded `qbittorrent-nox@` instance carries `IPAddressDeny` covering `TV_NET`, as `systemctl show` reports it (so a drop-in never daemon-reloaded counts as missing). A WARN when one does not. | `WARN cotenants_denied: no IPAddressDeny=<TV_NET>: <units>`: that service relies on nftables alone to keep the TV out. | Re-run `install.sh`, which writes the drop-ins (`tvgw guard cotenants`) and reloads systemd. |
| `dnsmasq_caps` | Always | The running dnsmasq's effective capabilities (`CapEff` in `/proc/<pid>/status`) hold neither `net_admin` nor `net_raw`, and neither does its bounding set (`CapBnd`); the detail decodes `CapEff`. A WARN when either does. | `WARN dnsmasq_caps: ... holds net_admin` (or `net_raw`): `dhcp-broadcast` (or `no-ping`) is missing from the dnsmasq config, so dnsmasq kept the capability after its privilege drop and a DHCP-parser bug could rewrite the firewall. `WARN dnsmasq_caps: ... bounding set keeps net_admin and net_raw: the hardening drop-in is not in place`: `install.sh` took the drop-in out because dnsmasq would not serve with it, or it was never written; `CapEff` alone cannot show this, since with both config lines dnsmasq drops every capability with or without the drop-in. | `systemctl cat dnsmasq`, `ls /var/lib/tvgw/.unit-stamps/dnsmasq-refused`, and `journalctl -u dnsmasq` for the start that failed ([the hardening drop-in](../deploy/dnsmasq/README.md#the-hardening-drop-in)). |
| `flowlog_events` | Always | The flow log hears the TV ([design decision 43](design-decisions.md#43-the-flow-log-hears-the-tv-alone-and-the-gates-day-starts-at-each-answer)): `nf_conntrack_events` is `0` and the `ct_events` rule is in `inet tvgw`, and `tvgw-flowlog`'s main process (or a child of it) holds a conntrack event socket, found through `/proc/<pid>/fd` and the `Inode` column of `/proc/net/netlink` (protocol 12, non-zero `Groups`). The detail gives the socket's `Drops`, the events the kernel could not queue to it since the logger started; with `--record` they go into `fw_counters` as `flowlog: event socket drops`, and the ingest warns when they grew. A WARN when the switch is not `0`: the flow log works, but every connection on the Pi reaches its socket again. | `nf_conntrack_events=0 and no ct_events rule: the flow log records nothing`: the rule is gone (a hand edit, or a rollback to an older `tvgw-apply`). `tvgw-flowlog has no running process`, `holds no conntrack event socket`: the logger is down or not listening. `cannot read /proc/<pid>/fd (run as root)`. | For the first, `sudo tvgw-apply`; after a rollback, `sudo sysctl -w net.netfilter.nf_conntrack_events=2` ([rolling back the code](operations.md#rolling-back-the-code)). For the others, `systemctl status tvgw-flowlog` and `journalctl -u tvgw-flowlog -n 20`. For the WARN, `sudo tvgw-apply`. |

### In plain words

Each check also has three short plain texts for a reader who is not an engineer: what it means, what you notice on the TV, and the fix (`PLAIN` in src/tvgw/verify.py). `GROUPS` sorts the checks under five plain sentences, listed below in their order. `SETTLING` names the checks that can fail for a few minutes after an install or a restart, while the blocklists download and the services start, and then pass on their own: `list_sentinels`, `doh4_loaded`, `doh4_fresh`, `services`, `capture`, `flowlog_events` and `resolver_must_allow`. tests/unit/test_verify_plain.py fails when a check has no plain entry or no group, when a fix names a command or a unit this version does not have, and when the list or the table below differs from the code.

- the TV's cable leads to the internet only through this computer: `ruleset`, `ruleset_unchanged`, `applied_current`, `forwarding`, `ipv6_off`, `ipv6_guard`, `tv_route`, `policy_rule`, `guard_present`, `guard_quiet`, `cotenants_denied`, `dnsmasq_caps`
- the TV's lookups go through the filter: `vpn_dnat_idle`, `resolver_rewrite`, `resolver_must_allow`, `list_sentinels`, `doh4_loaded`, `doh4_fresh`, `adguard_version`, `adguard_pinned`, `dnsgate`
- recording what the TV does: `capture`, `flowlog_events`
- every service is running: `services`
- the TV has no second way out: `tv_paths`

| Check | What it means | What you notice | The fix |
|---|---|---|---|
| `ruleset` | The gateway's firewall is not loaded, or one of its main rules is missing. | Usually the TV has no internet. If the firewall was removed by hand, the TV may be online unfiltered. | Run `sudo systemctl start tvgw`, then `sudo tvgw-apply`, and read any error it prints. |
| `ruleset_unchanged` | The firewall rules were changed after the gateway last set them. | Nothing on the TV, unless the change lets something through. | Run `sudo tvgw-apply`. It sets the gateway's own rules again. |
| `applied_current` | A firewall setting or list was changed, and the gateway has not put the change in force. | Nothing on the TV: the rules from before the change still hold. | Run `sudo tvgw-apply`, and read any error it prints. |
| `forwarding` | The gateway is not passing the TV's traffic on to the internet. | The TV has no internet. | Run `sudo systemctl start tvgw`, then `sudo tvgw-apply`. |
| `ipv6_off` | IPv6, the newer kind of internet address, is switched on for the TV's port. The gateway handles only the older kind, so IPv6 must stay off there. | Nothing on the TV. One of the two walls against IPv6 is down. | Run `sudo tvgw-apply`. |
| `ipv6_guard` | The second wall against IPv6 on the TV's port is missing. The first, IPv6 switched off, still holds. | Nothing on the TV. | Check that the TV's cable is plugged in and the TV is on, then run `sudo tvgw-apply`. It cannot add this wall while the TV's port is down. |
| `tv_route` | The TV's traffic has no way out to the internet, or would leave by the wrong connection. | The TV has no internet. | Check that the gateway itself is online, then run `sudo tvgw-apply`. It also runs on its own when the gateway's connection comes back. |
| `policy_rule` | The rule that sends the TV's traffic out by the gateway's direct connection is missing. | The TV's traffic may leave by another route, such as a VPN on the gateway. | Check that the gateway itself is online, then run `sudo tvgw-apply`. |
| `vpn_dnat_idle` | Some of the TV's lookups reached the VPN program's own redirect instead of the filter. | Nothing on the TV. Those lookups were not filtered. | Run `sudo tvgw-apply`. The check passes again once the VPN program reloads its rules, which starts its count from zero. |
| `doh4_loaded` | The list of encrypted lookup services the TV may not use is empty or too short. | Nothing on the TV, but it could look names up around the filter. | Run `sudo systemctl start tvgw-doh-update`, then check again with `sudo tvgw verify`. If it still fails, see why with `journalctl -u tvgw-doh-update -n 20`. |
| `doh4_fresh` | That list of encrypted lookup services has not been updated for over a week, or is missing. | Nothing on the TV. Services added to the list since then are not blocked. | Run `sudo systemctl start tvgw-doh-update`. If it fails, see why with `journalctl -u tvgw-doh-update -n 20`. |
| `resolver_rewrite` | The filter does not send the TV's requests for its maker's file service to the gateway's web filter. | App installs and updates may fail, or those requests go out unchecked. | Run `sudo tvgw adguard apply`, then check again with `sudo tvgw verify`. |
| `resolver_must_allow` | A name the TV needs, such as its clock or its app store, is blocked or gets no answer. | The TV may show the wrong time or certificate errors, apps may not load, or it may say it has no internet. | Right after setup or a restart, wait 5 minutes and check again with `sudo tvgw verify`. If it still fails, check that the gateway is online, then run `sudo tvgw adguard apply`. |
| `services` | One of the gateway's programs or scheduled jobs is not running. Its name is on this check's line in the output of `sudo tvgw verify`. | It depends on which. If tvgw itself or the filter stopped, the TV has no internet. If the program that gives the TV its address stopped, the TV loses the internet the next time it asks for an address. If a scheduled job stopped, the brief stops updating. | Start it with `sudo systemctl start <name>`, or for a name ending in .timer, `sudo systemctl enable --now <name>`. Then see why it stopped with `journalctl -u <name> -n 20`. |
| `tv_paths` | The TV reports a second connection, such as Wi-Fi or Wi-Fi Direct, that goes around the gateway. | Nothing on the TV. Whatever it sends that way is neither filtered nor recorded. | On the TV, switch Wi-Fi off, forget every saved network, and switch off Wi-Fi Direct and any tethering. Then see what the TV reports now with `sudo tvgw tvcheck`. This check clears with the next hourly reading. |
| `adguard_version` | The filter (AdGuard Home) is missing, older than the release with the 2026 security fixes, or does not say which version it is. | If it is missing, the TV gets no answers to its lookups. If it is old, it has a known security hole. | Install or update it with the command on this check's line in the output of `sudo tvgw verify`, then check again with `sudo tvgw verify`. If the line names no command, ask for help on the project's issue tracker. |
| `list_sentinels` | The filter has not loaded one of its blocklists, or a list arrived empty. | Nothing on the TV. The trackers on that list are not refused. | Right after setup, wait 5 minutes: the lists may still be downloading. Then check again with `sudo tvgw verify`. If it still fails, see why a download failed with `journalctl -u AdGuardHome -n 50`. |
| `adguard_pinned` | The filter (AdGuard Home) could replace itself with a new version that tvgw has not checked. | Nothing on the TV. | Run `sudo tvgw adguard service`. |
| `dnsgate` | The gateway's count of connections to addresses the TV never looked up is missing. A warning instead says its list is more than half full. | Nothing on the TV. Without the count, the brief cannot show those connections. | Run `sudo tvgw-apply`. A warning alone needs no fix: the TV, or the program that fills the list, is doing something new. |
| `capture` | The recording of the TV's traffic is set up wrong: two recorders run at once, or the one in use receives nothing. | Nothing on the TV. The brief counts some connections twice, or the recording stays empty. | Run `sudo systemctl restart tvgw-pcap`, then `sudo tvgw-apply`. |
| `guard_present` | The gateway's second firewall, which keeps the TV away from this computer's own services, is missing or changed. | Nothing on the TV. If the main firewall also goes, the TV could reach this computer's other services. | Run `sudo systemctl reload-or-restart tvgw-guard`. |
| `guard_quiet` | The second firewall stopped traffic from the TV that the main firewall let through: the two disagree. | Nothing on the TV: the second firewall held. | Run `sudo tvgw-apply`. If the warning comes back, ask for help on the project's issue tracker. |
| `cotenants_denied` | Another program on this computer is kept from the TV only by the firewall, not also by a setting of its own. | Nothing on the TV. | Run the installer again, which adds that setting: `sudo /usr/lib/tvgw/deploy/install.sh` (from a source checkout, `sudo deploy/install.sh`). |
| `dnsmasq_caps` | The program that gives the TV its address kept a permission it does not need, one that could change the firewall. | Nothing on the TV. | Run the installer again: `sudo /usr/lib/tvgw/deploy/install.sh` (from a source checkout, `sudo deploy/install.sh`). If the warning stays, ask for help on the project's issue tracker. |
| `flowlog_events` | The gateway's log of the TV's connections is not recording, or it hears every connection on this computer instead of the TV's alone. | Nothing on the TV. The brief misses connections, or the log can lose some when this computer is busy. | Run `sudo tvgw-apply`, then `sudo systemctl start tvgw-flowlog`. Check again with `sudo tvgw verify`: this check needs root. |

| Content Store blank or failing (error 202) | `us.lgrecommends.lgappstv.com`, the store's landing feed, is blocked, or the file-service names are unreachable. | `tvgw host us.lgrecommends.lgappstv.com` must show `state=allowed`. `tvgw gfts 1d` for 403s. `systemctl status nginx`. | Act as the must-allow red line says; restart nginx if it is down. |

| One app broke after a policy change | A new block, or a list that changed. | `tvgw rules` and the brief's Rule changes. `tvgw host <name>` for the names the app uses. | Revert the rule in the profile and deploy ([changing policy](operations.md#changing-policy)). ## Failed units

`systemctl --failed` lists a unit whose last run failed. Read its journal first ([reading the journals](../deploy/systemd/README.md#reading-the-journals)); each unit's schedule and start timeout are in [units](../deploy/systemd/README.md#units). Rows are in alphabetical order.

| Unit | Fails when | What it means | What to do |
|---|---|---|---|
| `tvgw.service` | `tvgw-apply` exits non-zero on a start: `BLOCK_QUIC`, `STRICT_PORTS` or `ADTECH_PORT_WALL` not exactly `yes` or `no`, `UPLINK` or `DNSGATE` out of range, `WAN_GW` unset with `UPLINK=direct`, `VPN_IF` not `auto`, `none` or an interface name other than `lo`, `TV_IF` and `WAN_IF`, `UPLINK=vpn` with `VPN_IF=none`, nft rejecting the ruleset, or its start timeout running out. | Forwarding is switched on last, so after a failed start the TV is dark: it fails closed ([design decision 5](design-decisions.md#5-fail-closed)). | `journalctl -u tvgw -n 20` shows the `tvgw:` error. Fix `/etc/tvgw/tvgw.conf` or `/etc/tvgw/block4.txt`, then run `sudo systemctl start tvgw`. |
| `tvgw-analyst.service`, `tvgw-analyst-weekly.service` | A request failed (the key refused, the API unavailable, the answer cut off at `MAX_TOKENS`, another client error), the key file is readable by others, or its start timeout runs out. | No proposals for that window. A failed window is not asked again: the next scheduled run reads its own window. | Read the message in [the analyst and autonomous blocks](#the-analyst-and-autonomous-blocks). Ask again for the missed window by hand ([running it by hand](analyst-and-autonomy.md#running-it-by-hand)). |
| `tvgw-analyze.service` | Its start timeout runs out, or a step outside ingest and the report writes fails under `set -e`. Ingest warnings and a failed report print `tvgw-analyze: WARNING: ...` and do not fail it. | The hourly ingest and reports may be behind. Coverage shows `NOT ASSESSED` once a source goes unread. | Read `journalctl -u tvgw-analyze -n 50`. Run `sudo tvgw ingest` to see its warnings. |
| `tvgw-autoblock.service` | A revert could not re-apply AdGuard, or another error. | A reverted machine rule is out of `auto.rules` but still in AdGuard. | Run `sudo tvgw adguard apply`, then `sudo tvgw autoblock check`. |
| `tvgw-backup.service` | `tvgw backup: FAILED: <reason>`: the copy failed `quick_check`, the disk is full, or the store stayed locked. | No copy today; older copies remain. The hardware suite fails once the newest copy is more than 36 hours old. | Free space, or check the store with `sudo tvgw sql "PRAGMA quick_check"`, then run `sudo systemctl start tvgw-backup`. A store that fails its own check needs [restoring a backup](operations.md#restoring-a-backup). |
| `tvgw-dnsgate.service` | tcpdump ends. The unit restarts on failure with a growing delay, so it shows as restarting more often than as failed. | The gate set stops filling, so the gate's count overstates. `services` in `tvgw verify` reports it down. | `journalctl -u tvgw-dnsgate` carries tcpdump's own error and `tvgw dnsgate: tcpdump ended (rc=<N>)`. |
| `tvgw-doh-update.service` | The download failed, the list had under 50 entries (`tvgw: only <N> DoH IPs fetched; keeping old list`), `/etc/tvgw/doh-exclude.txt` is missing or empty, the final `tvgw-apply` failed, or its start timeout ran out. With `DOH_LIST_URL` unset it prints `tvgw: DOH_LIST_URL not set` and succeeds. | The old list stays loaded; `doh4_fresh` fails once it is 8 days old. | Read `journalctl -u tvgw-doh-update -n 20`, fix the cause, and run `sudo systemctl start tvgw-doh-update`. `doh-exclude.txt` comes from the repository: run the installer again. |
| `tvgw-guard.service` | `nft -f /etc/tvgw/guard.nft` fails at boot or at a reload: the file is missing or nft rejects it, or the load takes over a minute. | At boot the guard table is not loaded, so the Pi is open to the TV whenever `inet tvgw` is absent; `guard_present` FAILs. A failed reload leaves the table that was loaded. | `journalctl -u tvgw-guard -n 20`. Re-run `install.sh`, which renders `/etc/tvgw/guard.nft` again, checks it with `nft -c` and reloads the unit ([removing the guard in an emergency](operations.md#removing-the-guard-in-an-emergency) has the restore). |
| `tvgw-pcap.service`, `tvgw-pcap-headers.service` | `CAPTURE_MODE` is neither `full` nor `headers`, or the settings file cannot be sourced: both fail in `ExecCondition`. Or `/usr/bin/dumpcap` is missing or not executable by `tvgw-pcap`: the start fails with `... install wireshark-common ...`. | No capture at all. | Fix the setting, or install dumpcap as [what dumpcap needs](capture.md#what-dumpcap-needs) says, then `sudo systemctl restart tvgw-pcap`. |
| `tvgw-flowlog.service`, `tvgw-pcap.service` | They restart whenever they exit (`Restart=always`), so a fault shows as repeated restarts. They start after `tvgw.service` (`After=`, `Wants=`) but are not bound to it: a stopped or failed apply does not stop the capture. | A gap in the flow log or in the captures. The brief's red line `TV was on but no connections were recorded` names a dead flow log. | Read `journalctl -u tvgw-pcap -u tvgw-flowlog`. |
| `tvgw-prune.service` | `tvgw prune-pcaps` printed a warning. | Retention kept a file it should have deleted, deleted an unread one, or could not tell which file the capture is writing. | Look the warning up in [retention warnings](#retention-warnings). |
| `tvgw-verify.service` | A check failed, the run could not be stored, or its start timeout ran out. | The last check found a FAIL. | Run `sudo tvgw verify` and see [what tvgw verify checks](#what-tvgw-verify-checks). |

`AdGuardHome`, `dnsmasq` and `nginx` are not tvgw's units, but `services` checks them. Read `systemctl status` for each.

## Ingest warnings

`tvgw ingest` prints each warning to stderr as `tvgw ingest: WARNING <text>` and stores it with the run in `ingest_runs`. The brief lists the warnings of the runs that fed its window as `ingest warning: <text>`, and the red line `ingest warnings: <N>` counts them ([red lines](operations.md#red-lines)). Any warning fails the command. A source whose step failed, or whose input is missing, is not stamped as read, so Coverage calls it `NOT ASSESSED`.

Rows follow the order in which ingest reads the sources: flows, dns, gfts, tvstate, oddport, gate, adport, rules, then the pcaps (`run` in `src/tvgw/ingest.py`).

| Warning | What it means | What to do |
|---|---|---|
| `<source>: <path> is missing` | The source's input does not exist: the unit that writes it is down, or a path is wrong. The TV-state history is exempt, since only profiles with a LAN-API reader write it. | For `flows`, run `systemctl status tvgw-flowlog`. For `dns`, check AdGuard's query log (`sudo tvgw adguard diff` shows whether `querylog.file_enabled` drifted). For `gfts`, check nginx. For `pcaps`, the installer creates `/var/lib/tvgw/pcap`. |
| `<source>: log rotated or truncated since the last run and the lines written before it could not be recovered` | Lines were lost between two reads of a log: it rotated more than once between reads, or was truncated. | A one-off costs that gap. If it repeats, check that the hourly ingest runs. |
| `flows: <N> malformed line(s) skipped` | conntrack lines that do not parse, or hold a value SQLite cannot store. | A one-off needs nothing. Every hour means conntrack's output changed. |
| `flows: conntrack lost events <N> time(s) since the last run (ENOBUFS, first at <time>): connections that ended then are not in the store` | conntrack's netlink buffer overflowed: it dropped events, said `We have hit ENOBUFS! We are losing events.` in `tvgw-flowlog`'s journal, and carried on. The flow sections undercount around that time, and nothing else shows it, since `flows.log` reads as whole. | `journalctl -u tvgw-flowlog -g ENOBUFS` shows when. A card or CPU saturated at that moment (a backup, an upgrade) is the usual cause; repeated losses under ordinary use are a fault to report. If the journal itself cannot be read, the flows step fails with a `flows:` error instead and is checked again next run. |
| `flows: the flow logger's event socket dropped <N> event(s) since the last run (first seen by tvgw verify at <time>): connections that ended then are not in the store` | The kernel's count of events it could not queue to `tvgw-flowlog`'s socket grew between two `tvgw verify --record` snapshots (`flowlog: event socket drops` in `fw_counters`). The same loss as the `ENOBUFS` warning above, counted by the kernel, so it survives a reboot that erases the journal. A lower count than before is a restarted logger, and all of it is new. | As for the `ENOBUFS` warning. With only the TV's connections making events ([design decision 43](design-decisions.md#43-the-flow-log-hears-the-tv-alone-and-the-gates-day-starts-at-each-answer)), a loss means the logger itself stalled: check `systemctl status tvgw-flowlog` and the card. |
| `dns: <N> malformed query-log record(s) skipped` | Torn or NUL-filled lines in AdGuard's query log; counted, never fatal to the hour. | A one-off needs nothing. Every hour means the query log's format changed. |
| `gfts: <N> malformed line(s) skipped` | URL-filter log lines not in the `tvgw_gfts` format. | Check that the installed nginx config carries `log_format tvgw_gfts` from `deploy/nginx/tvgw-gfts.conf`; a unit test ties the parser to it. |
| `rules: <kind>: <error>` | A policy file could not be read: `gfts-block` (the nginx config), `block4` or `adguard` (`AdGuardHome.yaml`). That kind's rules stay in the history unretired. | Fix the path or the permissions. |
| `rules: <kind>: not in a form we can read` | The file holds no rules in the shape ingest parses, such as an `AdGuardHome.yaml` without a `user_rules` list. | Check the file. |
| `pcaps: cannot tell which file the capture is writing (needs /proc and root); skipped this run` | Ingest ran without root or without `/proc`, so no pcap was read. The pcaps are not stamped as read (`SourceSkipped`), so Coverage says `NOT ASSESSED` for them rather than an hour with no rows. | Run ingest as root; the unit does. |
| `pcaps: <N> file(s) deferred to the next run (time budget)` | A backlog: tshark gets `PCAP_BUDGET = 20 * 60` seconds per run. | Nothing; it clears by itself. |
| `<pcap>: not a capture file (<size> bytes)` | A finished file shorter than a pcap header (`PCAP_HEADER = 24` bytes), recorded as unreadable without running tshark. | Nothing; retention deletes it. |
| `<pcap>: <error>; recorded as unreadable after 24 attempts` | tshark failed on the file in `PCAP_MAX_ATTEMPTS = 24` attempts, counted at most once per clock hour, so a day of failures however often ingest ran; the store gave up on it. It is never retried, and retention may delete it. | After fixing the cause, delete its mark so the next run retries it (below). |
| `<pcap>: <N> connection attempts to :443 but no TLS hello: check the capture filter and tshark` | At least `SYN_CHECK = 20` connection attempts to port 443 and no hello: an extraction fault, which otherwise looks like a quiet hour. | Check that the installed `tvgw-pcap.service` matches the repository (`tests/unit/test_capture_filter.py` guards its filter) and that tshark reads the file. |
| `<N> pcap(s) could not be read (<pcap>: <error>); will retry next run` | tshark failed on these files: `tshark rc=<N>: <stderr>`, `refusing to run tshark as root: systemd-run not found`, or a timeout. Each is retried on every run, its failures counted at most once per clock hour, up to 24 attempts. When no pending file could be read in the run, the pcaps are not stamped as read and Coverage says `NOT ASSESSED`. | Fix the cause. In the 2026-10-27 incident the extractor, running as `nobody:nogroup`, could not read the files ([incidents](incidents.md)). |
| `<source>: <exception>: <message>` | Any other failure of a step, such as `oddport: RuntimeError: journalctl rc=<N>: ...` when the journal cannot be read. The step rolled back. | Run `sudo tvgw ingest` to see it again, and read the message. |

To have ingest retry a pcap recorded as unreadable, delete its mark from `pcaps_done` while the file is still in place. On the Pi:

```sh
sudo /opt/tvgw-venv/bin/python -c 'import sqlite3; c = sqlite3.connect("/var/lib/tvgw/tvgw.db", timeout=60); c.execute("DELETE FROM pcaps_done WHERE name = ?", ("<pcap>",)); c.commit()'
```

### Retention warnings

`tvgw prune-pcaps` prints these as `tvgw prune-pcaps: WARNING <text>` and fails, so `tvgw-prune.service` shows in `systemctl --failed`. They are not in the brief. What retention keeps and why is in [raw pcaps](privacy-and-retention.md#raw-pcaps). Rows follow the order of `prune` in `src/tvgw/pcaps.py`.

| Warning | What it means | What to do |
|---|---|---|
| `cannot tell which file the capture is writing; nothing deleted` | Prune could not read the capture's open files: not root, or no `/proc`. | Run it as root; the unit does. |
| `<pcap>: never ingested, deleted at twice PCAP_DAYS` | Evidence was lost: the file was never read into the store. | Fix ingest; the hour in that file is gone. |
| `<N> finished pcap(s) older than PCAP_DAYS kept: not ingested yet` | Files due to go have not been read yet. | Find why ingest is not reading pcaps in the table above. |
| `pcaps over PCAP_MAX_GB by <N> MB with nothing ingested left to delete` | Every read file is gone and the unread ones still exceed the budget. | Fix ingest, or raise `PCAP_MAX_GB`. |
| `under 1 GB free where the pcaps live, with nothing ingested left to delete` | The filesystem is nearly full and only unread files remain. | Free space on that filesystem and fix ingest. |

## The analyst and autonomous blocks

`tvgw analyst`, `tvgw autoblock` and `tvgw undo` print one line per outcome, to the terminal or to their unit's journal (`run` in `src/tvgw/analyst.py`; `cmd_autoblock` and `cmd_undo` in `src/tvgw/cli.py`). How the analyst and its watches work is in [the analyst and autonomy](analyst-and-autonomy.md).

| Message | What it means | What to do |
|---|---|---|
| `tvgw analyst: no key at /etc/tvgw/claude.key; nothing sent (use --dry-run to see the pack)` | There is no key file. The run succeeds and sends nothing. | Expected without a key. |
| `PermissionError: /etc/tvgw/claude.key is readable by others (mode <mode>); chmod 600 it` | The key file has a group or other bit set. The run stops with a traceback and the unit fails. | Run `sudo chmod 600 /etc/tvgw/claude.key`. |
| `tvgw analyst: the key at /etc/tvgw/claude.key was refused (AuthenticationError)` | The API rejected the key. | Replace the key in the file. |
| `tvgw analyst: the API was unavailable (<error>); the next run will try again` | A rate limit, a connection failure, a timeout or a server error (`RateLimitError`, `APIConnectionError`, `APITimeoutError`, `InternalServerError`). The next scheduled run reads its own window, not this one. | Ask again for this window by hand ([running it by hand](analyst-and-autonomy.md#running-it-by-hand)). |
| `tvgw analyst: the answer was cut off at max_tokens; its cost is in <base>.json` | The answer reached `MAX_TOKENS` (64000, thinking included) before it was complete. It was billed: the `.json` record keeps the usage, the cost and `cut_off: true`, and the `.md` says nothing was proposed. The run exits 1, so the unit fails. | Ask again by hand; a lower `--effort` leaves more of the budget for the answer. |
| `tvgw analyst: <error>: <message>` | Any other failure. | Read the message, then ask again by hand. |
| `tvgw analyst: the model declined (<category>); see <file>.md` | The model's safety layer refused the window. The day's file says so, its `.json` records `refused` with the usage and the cost, nothing is proposed, and the run succeeds. | Read the file. |
| `tvgw analyst: <window>: nothing new, no request sent (use --force to ask anyway)` | `novelty` found nothing the store does not already know. A one-line file is written and nothing is spent. | Nothing; `--force` asks anyway. |
| `tvgw analyst: the weekly pass is off (ANALYST_WEEKLY_MODEL=off)` | The weekly pass is switched off in the settings. | Set `ANALYST_WEEKLY_MODEL` to a model to turn it on. |
| `tvgw analyst: no proposals yet` | `--show` found no proposals file. | Wait for the first run, or run one by hand. |
| `tvgw report: error: <reason>` from `tvgw analyst` | A usage error in the analyst's flags, such as `--day, --since, --week and --weekly exclude each other`. The prefix names `tvgw report` although the command was `tvgw analyst`. | Fix the flags ([commands](../src/tvgw/README.md#commands)). |
| `tvgw autoblock: <verdict> <rule> (<reason>)` | The hourly check decided on a machine rule: `passed`, or `reverted` with the reason. | For `reverted`, the rule is already out of the file and AdGuard; read the reason. |
| `` tvgw autoblock: WARNING: a reverted rule is still in AdGuard; run `tvgw adguard apply` `` | A revert took the rule out of the file, but AdGuard's re-apply failed. The decision's reason in the store says so, and the unit fails. | Run `sudo tvgw adguard apply`; if that fails, see [AdGuard apply failures](#adguard-apply-failures). |
| `tvgw autoblock: <N> rule(s) on probation, nothing to decide` | Nothing was due this hour. | Nothing. |
| `tvgw undo: <rules> removed and AdGuard re-applied` | `tvgw undo` took the rules out. | Wait out the blocked answer's TTL before you test ([after unblocking something](operations.md#after-unblocking-something)). |
| `tvgw undo: no machine rule to remove` | The record holds no active machine rule. | A line in `/var/lib/tvgw/auto.rules` with no record is not removed by `tvgw undo`: delete it by hand and run `sudo tvgw adguard apply`. |
| `tvgw undo: the rules file was changed but AdGuard was not re-applied (<error>)` | The rule is out of the file, but AdGuard still has it. | Run `sudo tvgw adguard apply`. |
| `tvgw adguard: machine rule dropped: <rule>: <problem>` | A line in `auto.rules` fails the profile's lint beside the profile's rules, for example because it covers a must-allow host, so it never reaches AdGuard. Any apply prints this to stderr. | Delete the line from `/var/lib/tvgw/auto.rules`. The hardware test `test_autoblock_file_record_and_resolver_tell_one_story` fails while it is there. |

## AdGuard apply failures

`tvgw adguard apply` runs by hand and from the installer. It lints the profile, validates the candidate config with `AdGuardHome --check-config`, copies the live file to a `.bak-*` backup, stops AdGuard Home, moves the candidate into place, starts it, and waits up to 30 seconds for the resolver to resolve the profile's first must-allow name with NOERROR or NXDOMAIN (`apply` and `dns_ready` in `src/tvgw/adguardcfg.py`). The analyst after an autonomous block or a canary revert, the hourly check after a revert, and `tvgw undo` run the same apply without the profile lint (`adguardcfg.apply()` through `analyst.adguardcfg_apply`; the machine's rules are still linted one by one), and their readiness probe asks for `example.com`; their failures are the rows of [the analyst and autonomous blocks](#the-analyst-and-autonomous-blocks) (`no: AdGuard did not take it (<error>)` on a proposal, the hourly check's warning, `tvgw undo`'s message). A failure from the stop onwards puts the backup back and restarts AdGuard. In the installer, a failed apply stops the install at that step. Rows follow the order in which the command can fail.

| Message | What it means | What to do |
|---|---|---|
| `tvgw adguard: the profile does not lint: <problems>` | The profile fails its lint, so nothing was planned. | Fix the profile; `tvgw profile` lists the problems. |
| `tvgw adguard: DNS_UPSTREAMS is empty` | The setting names no upstream. | Set `DNS_UPSTREAMS` ([the settings file](../deploy/README.md#the-settings-file)). |
| `cannot read /opt/AdGuardHome/AdGuardHome.yaml: <error> (is AdGuard Home installed and set up?)` | There is no config to merge into. | Run `sudo tvgw adguard install` ([installing it without the wizard](adguard.md#installing-it-without-the-wizard)), or install AdGuard Home and finish its first-run wizard ([the install guide](install.md#step-2-install-what-tvgw-needs)). |
| `tvgw adguard: another tvgw adguard apply is running` | The lock beside the config, `.tvgw-adguard.lock`, is held by a deploy, the analyst, the hourly check, `tvgw undo` or another hand run. Nothing changed. | Wait for the other apply to finish, then run it again. |
| `tvgw adguard: <path> has no schema_version (empty or truncated); restore a .bak-* file or rerun AdGuard's wizard; nothing changed` | The live config is damaged; apply refuses to complete it from a template. | Restore the newest good copy ([rolling back AdGuard alone](operations.md#rolling-back-adguard-alone)) or rerun AdGuard's wizard. |
| `tvgw adguard: <path> is at schema_version <N>, above 34, the newest this tvgw release has been tested with; nothing changed. ...` | (lists) AdGuard Home is newer than tvgw has been tested with (it updated itself, or a 1.x release was installed) and migrated its config past schema 34 (`SCHEMA_CEILING` in src/tvgw/adguardcfg.py). The resolver runs as it is; nothing is written. | Update tvgw to a release that knows the schema, or go back by hand: stop AdGuardHome, copy the `AdGuardHome.bak-*` binary and the `AdGuardHome.yaml.bak-*` of the same stamp into place, start it, run `sudo tvgw adguard diff` ([the schema ceiling](adguard.md#the-schema-ceiling)). `tvgw adguard upgrade` refuses this state too. |
| `tvgw adguard: cannot read one ExecStart from <unit file>; add --no-check-update by hand` | (lists) `tvgw adguard service` found no `ExecStart=` in the unit's `[Service]` section, or more than one, so it cannot know which command to repeat with the flag. Nothing was written. | Read the unit with `systemctl cat AdGuardHome` and write the drop-in by hand: an empty `ExecStart=`, then the full command with `--no-check-update`; then `sudo systemctl daemon-reload && sudo systemctl restart AdGuardHome`, and `sudo tvgw verify` shows `adguard_pinned`. |
| `tvgw adguard: deferred: upstream down (a fresh lookup under <name> SERVFAILs, or goes unanswered while AdGuard answers its own rules); ...`, exit 3 | (lists) The restart guard: the upstreams answer nothing (SERVFAIL, or silence past AdGuard's own upstream timeout while its filter still answers), so a restart would empty the cache the TV is living on. Nothing was staged or restarted ([the restart guard](adguard.md#the-restart-guard)). The analyst, the hourly check and `tvgw undo` report the same text. | Check that the Pi reaches the DoH upstreams (`journalctl -u AdGuardHome`, the VPN client), then run the command again. |
| `tvgw adguard: not validated: <binary> not found; the planned config was not validated before writing` | Not a failure: there is no `AdGuardHome` binary beside the config, so the check was skipped. | Check where AdGuard Home is installed. |
| `tvgw adguard: AdGuard Home rejected the planned <path>; nothing changed`, then AdGuard's own reason | `AdGuardHome --check-config` refused the candidate before the service was touched, or did not finish in 120 seconds. | Fix what AdGuard's reason names, in the profile or the settings. |
| `tvgw adguard: <error>; the previous config (<backup>) was put back` | A step from the stop onwards failed and the rollback worked. `AdGuardHome did not answer DNS after the change` means the resolver did not resolve the must-allow name within 30 seconds; SERVFAIL counts as not ready, so a deploy while the DoH upstreams are unreachable ends here. | Check that the Pi reaches the upstreams, then apply again. |
| `tvgw adguard: <error>; restoring <backup> also failed: <error>` | The rollback failed too. AdGuard may be stopped, or running the planned file. | Restore the named backup by hand ([rolling back AdGuard alone](operations.md#rolling-back-adguard-alone)) and run `sudo tvgw verify`. |

## AdGuard install failures

`sudo tvgw adguard install` ([installing it without the wizard](adguard.md#installing-it-without-the-wizard)) stops with one line and exit 1, and leaves nothing half done. A stop from the first run on ends with what the run took back: `removed <files>; the binary in /opt/AdGuardHome stays`, where the files are the `AdGuardHome.yaml` and the password file that run wrote, or `nothing was removed; ...`. Run the command again once the cause is fixed. The constants named below are in `src/tvgw/aghinstall.py`. Rows follow the order in which the command can stop.

| Message | What it means | What to do |
|---|---|---|
| `tvgw adguard: another tvgw adguard install is running` | The lock `/var/lib/tvgw/.adguard-install.lock` is held. Nothing changed. | Wait for the other run to finish. |
| `tvgw adguard: AdGuard Home is already set up on this computer, and not by tvgw. ...` | tvgw's marker is missing, and its `AdGuardHome.yaml` holds neither the TV's client entry nor the profile's must-allow exceptions, or cannot be read. It most likely serves other devices ([whose AdGuard it is](adguard.md#whose-adguard-it-is)). Nothing changed. | Use a separate computer for tvgw. Only if no other device uses this AdGuard, run `sudo tvgw adguard apply` to let tvgw take it over. |
| `tvgw adguard: AdGuard Home in /opt/AdGuardHome is tvgw's but below v0.107.79; run sudo tvgw adguard upgrade --fetch` | The binary is older than `verify.ADGUARD_MIN`. Nothing changed. | Run `sudo tvgw adguard upgrade --fetch` ([upgrading AdGuard Home](adguard.md#upgrading-adguard-home)). |
| `tvgw adguard: tvgw pins AdGuard Home for 64-bit arm64 and amd64 Linux; this computer is <machine> with a <bits>-bit system; nothing was installed` | `aghinstall.PIN` has no asset for this computer, or the system is 32-bit on a 64-bit processor. | Use a 64-bit system on an arm64 or amd64 computer. |
| `tvgw adguard: could not download AdGuard Home from <url>: <error>; nothing was installed` | GitHub did not answer, or the system's certificates could not check its answer (`certificate verify failed`). | Check the uplink, and that the `ca-certificates` package is installed. |
| `tvgw adguard: the downloaded AdGuard Home does not match tvgw's pinned hash; nothing was installed` | The file that arrived is not the release tvgw pins. It was deleted. | Do not install it another way. Run the command again later; if it repeats, open an issue with the message. |
| `tvgw adguard: the download from <url> is over 64 MB; nothing was installed`, or `tvgw adguard: the AdGuard Home archive holds <member> ...` | The answer, or the archive in it, does not have the shape of the pinned release (`MAX_DOWNLOAD`, and the member filter of `aghinstall.extract()`). Nothing was written to `/opt/AdGuardHome`. | As for the hash. |
| `tvgw adguard: systemd-run could not start AdGuard Home's first run: <error>; ...` | systemd refused the transient unit `tvgw-adguard-firstrun`. | Read the error; `systemctl status tvgw-adguard-firstrun` shows a unit left by an earlier run. |
| `tvgw adguard: AdGuard Home did not start its first run within 30 seconds (journalctl -u tvgw-adguard-firstrun); ...`, or `... stopped before its wizard answered ...` | The binary did not serve its wizard on loopback within `WIZARD_WAIT`. | Read the journal it names. |
| `tvgw adguard: port 53 on 127.0.0.1 is not free for AdGuard Home: <reason>; port 53 is held by <holder>; ...` | Another DNS server holds `127.0.0.1:53`, and AdGuard's own check refused the address before anything was configured. The holders come from `ss`, each as `<name> (pid <pid>) on <address>`, every socket on port 53 among them: systemd-resolved's on `127.0.0.53` is listed too, and is not the one in the way. | Stop or remove the program on `127.0.0.1:53` or on `0.0.0.0:53`, or use a separate computer for tvgw. |
| `tvgw adguard: port 3000 on 127.0.0.1 is not free for AdGuard Home's page: <reason>; ...` | Another program holds the page's address. | Stop it, or use a separate computer for tvgw. |
| `tvgw adguard: AdGuard Home refused tvgw's first-run settings (<status>): <reason>; ...`, or `... did not take tvgw's first-run settings ...` | AdGuard's install API answered with an error; the reason is AdGuard's own. | Fix what the reason names. |
| `tvgw adguard: <yaml> holds <n> user(s) (<names>), not tvgw's one 'admin': something else may have answered AdGuard Home's wizard first; ...`, or `... the password tvgw set does not open AdGuard Home's page ...` | The YAML AdGuard wrote is not the answer tvgw gave: another process on this computer answered the open wizard first, or changed its user. The run removed that YAML. | Find what else runs on the computer before you run the command again. |
| `tvgw adguard: AdGuard Home's page did not come up at http://127.0.0.1:3000 after its wizard; ...` | After the wizard, AdGuard did not move its page to `127.0.0.1:3000` within `LOGIN_WAIT` (10 s). | Read `journalctl -u tvgw-adguard-firstrun`. |
| `tvgw adguard: AdGuard Home's service did not start: <error>; ...` | AdGuard's own `-s install`, or the start of the unit its install script left, failed. That unit is left stopped, so no open wizard stays on AdGuard's default address. | Read `journalctl -u AdGuardHome`. |
| `tvgw adguard: ADGUARD_LISTEN is keep, so AdGuard Home answers DNS on 127.0.0.1 alone and the TV, which asks <GW_IP>, gets no answer: ...` | Not a failure: the install worked, and with `keep` the apply leaves DNS where the wizard put it ([the listen setting](adguard.md#the-listen-setting)). | Set `ADGUARD_LISTEN=gateway` in `/etc/tvgw/tvgw.conf`, then run `sudo tvgw adguard apply`. |
