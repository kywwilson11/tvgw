# Deep dive, 2026-11-04: the four reports

These are the four reports of the third research pass, written on 2026-11-04 against release 0.3.0; the reports call it the second improvement pass, after a first of 2026-11-03 that is not in the repository. Each is kept as written, with a dated line under its title and its links rewritten for this folder. What the code took from them is in [the changelog](../../../CHANGELOG.md) under 2026-11-04, and the rest stays a proposal: check a claim against the code before acting on it.

| File | What it asked | What it found that changed the code |
|---|---|---|
| [R1-adjacent-repos.md](R1-adjacent-repos.md) | What adjacent projects do that tvgw could learn from: the shared blocklists, AdGuard Home and Pi-hole, network-isolation guides, other TVs' LAN APIs, measurement tools and documentation exemplars | HaGeZi Pro blocks 196 of LG's country clock hosts (`<cc>.nextlgsdp.com`), so the must-allow hosts follow the TV's country ([LG depth](../../../CHANGELOG.md#lg-depth-across-webos-generations-2026-11-04)). AdGuard Home drops a burst over 20 lookups a second from one /24 with no line in its log, so `tvgw adguard apply` owns `dns.ratelimit`, `dns.edns_client_subnet` and `dns.upstream_mode` ([AdGuard Home's bursts](../../../CHANGELOG.md#adguard-home-no-longer-drops-the-tvs-bursts-unseen-2026-11-04)). AdGuard's `check_host` names the rule that answers a name, so `tvgw check NAME` says why a name is blocked ([`tvgw check`](../../../CHANGELOG.md#tvgw-check-name-why-a-name-is-blocked-2026-11-04)) |
| [R2-lg-webos-versions.md](R2-lg-webos-versions.md) | What a gateway has to know about LG TVs after webOS 5, from webOS 6 to webOS 26 | LG's newer firmware refuses the signed manifest without a prompt, and a key that worked can stop after an update. A new pairing sends tvgw's unsigned, read-only manifest, a key the TV refuses is recorded and not sent again until the owner pairs, and the profile's generations table is keyed by the webOS release the TV reports in `hello` ([LG depth](../../../CHANGELOG.md#lg-depth-across-webos-generations-2026-11-04)) |
| [R3-docs-incremental.md](R3-docs-incremental.md) | How the documentation reads to its intended reader: a careful person with a smart TV, a spare Raspberry Pi and no networking knowledge | Its quick wins are in the pages: Wi-Fi forgotten before it is turned off, an ssh step that survives a paste, what a working install prints, the facts 0.3.0 made stale ([the pages after a read-through](../../../CHANGELOG.md#the-pages-after-a-read-through-2026-11-04)). Its finding F1, that `tvgw setup` from the package could not find `install.sh`, was fixed in 0.3.1 ([setup from the package](../../../CHANGELOG.md#setup-from-the-package-backups-on-a-small-card-the-scrubber-2026-11-04)) |
| [R4-samsung-depth.md](R4-samsung-depth.md) | What Samsung's Tizen TVs of 2019 to 2026 expose, refuse and break, deeper than the first pass | Pairing fails without a prompt on 2024 sets running One UI Tizen 9, so a Samsung is read every hour with one `GET /api/v2/` and no pairing, never keeping the reply's `ssid`, which holds the access point's BSSID. Four hosts the lists block had breakage reports, and both subscribed HaGeZi lists block the account-login host, so the Samsung profile keeps those five reachable ([a Samsung read without pairing](../../../CHANGELOG.md#a-samsung-read-without-pairing-and-its-profile-on-its-own-answer-2026-11-04)) |
