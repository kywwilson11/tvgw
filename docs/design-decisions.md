

## 82. Each rule and list is counted from the store; an allow unused for 30 days is named with the command that removes it, never removed

*2026-11-08, from the competitive-gap analysis's brief G7 ("what your own rules did, and which allows are holes you no longer need"). Built: counts per owner's rule in `tvgw rules --local` (with `--since` and `--json`), the refusals by list as the last section of `tvgw lists` (with `--since`), and the weekly report's Rule use section. Nothing is removed or changed on its own; no setting, no table, no column.*

**Context.** Firewalla's app 1.69 added rule usage statistics ([Residential Systems, 2026](https://www.residentialsystems.com/technology/connectivity/firewalla-releases-app-1-69-with-advanced-phishing-protection)); NextDNS ranks what each blocklist blocked, and "a query matching multiple blocklists counts once in each list's separate ranking" ([its API](https://nextdns.github.io/api/)); AdGuard Home's query log names the rule and the list behind every answer. tvgw has stored the rule and the list of every lookup since its first store (`dns.rule`, `dns.filter_id`), yet `tvgw rules --local` gave only each rule's day and reason. The owner could not see whether a block still did anything. More important for privacy, an allow written months ago to fix one app stays a hole in the protection after the app no longer needs it: the owner's allow carries `$important` and outranks every list's block and the machine's ([design decision 59](#59-site-rules-etctvgwlocalrules-written-by-tvgw-allow-and-tvgw-block-applied-after-the-profile-and-before-machine-rules-under-the-same-lint)).

**Decision.**

- **Counted from the store, by the rule's exact text, among the custom rules.** A block decided a lookup when the store's row is a refusal (`blocked = 1`) whose `rule` is the block's text; an allow decided one when AdGuard answered under it (`blocked = 0`, reason `NotFilteredAllowList`) and `rule` is the allow's text. The text compared is the file's line with its spaces stripped: the plan writes that line into `user_rules` as it is, and AdGuard names a custom rule by that text, case and modifier included, the comparison `tvgw check` makes to name a rule's source (`namecheck.source`); so `@@||news.example^$important` is not `@@||news.example^`. The store cuts `rule` at 2,000 characters; an owner's rule is far shorter. Only AdGuard's custom rules count (`filter_id` 0, or NULL for a row the log file wrote before 2026-11-07), so a list that carries the same text keeps its refusals. The store keeps the first rule AdGuard names for a lookup, the one that decided: a block whose names a list's rule decides first shows nothing, and still blocks if the list drops them. An allow counts every lookup it answered, whether or not a list would have refused it; what a rule would have done had it not been there is the probe's and the judge's question, not this one.
- **`tvgw rules --local`** adds, per rule, the lookups it decided in the last 7 and 30 days (`WINDOWS` in src/tvgw/rulestats.py), the distinct names in the 30 days, and the last time it decided one in the record. `--since SINCE` puts one window in place of the two, and `--json` prints everything as one object, for scripts and for a page later. It reads the `dns` rows of the owner's texts in one pass, since the store has no index on `rule`, and needs no more than `adm`.
- **An unused allow is named with the command that removes it, and nothing more.** An allow is named when it let nothing through in the 30 days before (`STALE_DAYS`), it was in force for all of them, and the record covers them: "Your allow of api.example.net let nothing through in 30 days. If no app needs it any more, remove it: sudo tvgw unallow api.example.net". In force means the plan takes it (the lint leaves it in) and every source that dates it puts it at least 30 days back: its comment line, by the end of its day, and the open row for its text in the rule history (`rules`). An allow either source makes younger, or neither dates, is not judged. The record covers the 30 days when its first ingest run is at least that old, `DB_DAYS` keeps at least 30 days, and its last run is within 2 hours of the window's end (`FRESH`, as `queries.STALE`); otherwise the output says why no allow is judged. `tvgw rules --local` and the weekly report name it; the plain brief does not, since this is a weekly task for whoever looks after the gateway. No code removes a rule: an allow is a hole only when no app needs it any more, which the owner alone knows. A TV unused for a month makes every allow look unused; the line says what the record saw.
- **The refusals by list** are the last section of `tvgw lists`, the list guard's command ([design decision 68](#68-a-lists-plain-exception-no-longer-lifts-the-profiles-red-line-blocks-the-lists-are-scanned-for-lines-that-act-on-the-tvs-rules-each-update-is-previewed-against-the-tvs-lookups-and-a-doh-list-refresh-that-drops-more-than-a-set-share-is-held-back)), after what the lists say about the TV's own rules; `--since SINCE` sets their window (default 7 days), its JSON carries them as `use` beside the guard's `state` and `previews`, and its exit status stays the guard's. They give each list AdGuard's settings switch on, by the name the profile gives its URL (`namecheck.list_names`), with the lookups it refused, the distinct names and its five most refused names with their companies. Then come the profile's own rules, the owner's and the machine's, always shown, and two rows shown only when they counted something: custom rules none of tvgw's files hold now (drift, or a rule taken out since), and AdGuard's own features or a refusal with no rule named. A custom rule's text goes to the first of the profile, the owner and the machine that holds it, as `adguardcfg.rule_groups` orders them. The owner's texts include each one the change ledger says an owner's command wrote, and the machine's every row of `auto_rules`, so a rule removed within the window keeps its row. Every refusal of the window lands in exactly one row, so the rows add up to the window's refusals. A list that refused nothing is said plainly, with `sudo tvgw verify` named where a sentinel checks that it is loaded, so the count and the sentinel check each other ([design decision 46](#46-the-blocklists-are-watched-and-adguard-changes-only-on-purpose)). AdGuard's settings file is AdGuard's own and may be readable by root alone: without it the lists go by AdGuard's number for them, a list that refused nothing cannot be shown, and the output says so. A name that is not an internet name is counted and never printed, as in `tvgw refused`.
- **The weekly report** ends with a Rule use section: the unused allows judged at the week's end, then the refusals by list over the week. A failure there is a report warning and costs no other section. The analyst's pack is built from `queries.window_report()` and does not carry it.

**Consequences.** The owner sees, per rule and per list, what the filter did for the TV, and an allow that stopped mattering is named every week with the one command that closes it. Nothing refuses traffic and nothing changes on its own. The counts are only as good as AdGuard's naming, one rule per lookup. A forgotten allow of a name the TV still asks for counts as used although no list may block that name any more; telling that case apart needs AdGuard asked about the name without the allow, which is not built. The machine's own rules get one row here and no counts of their own: the hourly judge already judges each of them ([design decision 20](#20-the-gateway-blocks-on-its-own-under-three-watches)).
